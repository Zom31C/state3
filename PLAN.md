# План: рантайм SKILL.state для агентов Qwen

**Источник:** arXiv:2608.26263 «SKILL.state: Scalable Long-Horizon Agent Skills» (Google/Purdue, v3, 02.09.2026), Appendix A (`#Ax1`) — шаблоны промптов четырёх рантаймов.

**Решение по скоупу:** автономный рантайм на TypeScript (Node.js) в этом репозитории, реализующий Algorithm 1 из статьи поверх моделей Qwen. Провайдеры: облачный API (DashScope / OpenRouter) и локальная Ollama за единым интерфейсом. Исходники самого Qwen Code не модифицируются.

## 1. Что именно переносится из статьи

### Ядро (обязательно)

| Элемент статьи               | Реализация                                                                                                                                                                    |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Процедурная спецификация `P` | Неизменяемый объект `Skill`: `instructions` (персона, пространство действий, правила среды) + статическая схема состояния. Схема пишется **один раз на домен**, не на задачу. |
| Состояние `Σ_t`              | Мутируемый JSON-объект, валидируемый zod-схемой. Хранится только то, что нужно для **будущих** шагов.                                                                         |
| Наблюдение `O_t`             | Текст последнего события среды (+ шумовая телеметрия в бенчмарке).                                                                                                            |
| Промпт (шаблон A.4)          | `instructions` + `Skill Execution State` (компактный `json.dumps(..., separators=(',',':'))`-эквивалент) + `Latest Observation` + инструкция формата ответа.                  |
| Выход LLM `(R_t, ΔΣ_t, a_t)` | Fenced JSON-блок ровно с двумя ключами: `{"state_patch": {...}, "action": "..."}`. Reasoning `R_t` **сбрасывается сразу после валидации** и в контекст не попадает.           |
| Оператор слияния `⊕`         | Детерминированный dict-merge: значение `null` удаляет ключ. `Σ_{t+1} = Σ_t ⊕ ΔΣ_t`.                                                                                           |
| Валидация и откат            | Схема принадлежит рантайму: невалидный патч **не может** испортить `Σ_t`. Откат к снапшоту + повторная генерация (см. §4).                                                    |
| Декодирование                | `temperature = 0.0`, `top_p = 1.0` — воспроизводимость.                                                                                                                       |

### Бейзлайны для сравнения (шаблоны A.1–A.3)

- **Prompt** (ReAct, append-only): весь транскрипт наблюдений/рассуждений/действий растёт.
- **Memory**: инструкции + NL-суммаризация прошлого (обновляется периодически отдельным LLM-вызовом) + окно из **3 последних ходов** + последнее наблюдение.
- **Stateful** (LangGraph-style): блок состояния **вместе с** полным растущим транскриптом.

### Метрики (как в статье)

1. **Точность** — доля валидных действий, совпадающих с ground-truth симуляцией.
2. **Средний размер промпта** — средняя длина строки промпта в символах на вызов.
3. **Суммарные токены** — накопленный расход за горизонт.

Ориентиры из статьи (Gemini-3-Flash, склад, T=100): Prompt 0.84 / Memory 0.87 / Stateful 0.91 / **SKILL.state 0.94**; средний промпт 36 362 → **1 905 символов**; токены 1.25M → **65k**.

## 3. Этапы работ

### Фаза 0 — Каркас проекта

1. Инициализация: `package.json`, `tsconfig` (strict), vitest, линтеры.
2. Конфигурация через `.env`: `PROVIDER=ollama|dashscope|openrouter`, имена моделей (по умолчанию для облака — напр. `qwen-plus`; для Ollama — локальная доступная модель), ключи.
3. Интерфейс `LLMProvider` + реализации трёх провайдеров; фиксация `temperature=0`, `top_p=1`; учёт токенов (`usage`) в каждом ответе.
4. **Критерий готовности:** `npm test` зелёный; один вызов модели через каждого провайдера возвращает текст и метрики токенов.

### Фаза 1 — Ядро рантайма (сердце проекта)

1. `StateStore`: deep-clone снапшот перед каждым шагом; оператор `⊕` с семантикой `null`-удаления; `rollback()`.
2. `prompts.ts`: все четыре шаблона дословно по Appendix A (A.4 — основной; A.1–A.3 нужны для сравнения в Фазе 3). `{skill.instructions}` подставляется динамически.
3. `parser.ts`: извлечение fenced JSON-блока; устойчивость к лишним пояснениям вокруг блока, отсутствию забора, хвостовым запятым (восстановление там, где возможно без потери данных). Ошибки классифицируются по трём категориям из статьи: синтаксис / типы / преждевременная перезапись.
4. `validator.ts`: zod-проверка патча до применения; неизвестные ключи и несоответствие типов → отказ; `null` допустим только как удаление.
5. `runtime.ts` — цикл Algorithm 1:
   ```
   for t = 0..T:
     O_t ← env.observe()
     prompt ← build(skill, Σ_t, O_t)
     (R_t, ΔΣ_t, a_t) ← llm.complete(prompt)
     if ΔΣ_t невалиден → откат и повтор (см. §4)
     Σ_{t+1} = Σ_t ⊕ ΔΣ_t
     env.step(a_t)
   ```
6. **Критерий готовности:** модульные тесты на слияние/откат/парсер/валидатор; дымовой прогон цикла на тривиальной среде-заглушке с мок-провайдером (без сети).

### Фаза 2 — Складской бенчмарк (эквивалент SkillExecBench/Warehouse)

1. Генератор событий **строго по Algorithm 2**: `seed=42`, `rng`, 500 полок `shelf_0..shelf_499`; на каждом шаге `possible_events = [Receive]`, при наличии занятых полок добавляются `Order`, `Maintenance`; `rng.choice`; обновление ground-truth.
2. Наблюдения: `"Shipment arrived containing [item]"`, `"Customer ordered [item]"`, `"Maintenance required on [shelf]"` + блок `--- BACKGROUND TELEMETRY ---` (шум: батарея роботов, HVAC, OCR-логи камер).
3. Схема состояния: плоский словарь из 500 ключей `shelf_*: string|null`. Спецификация `P`: инструкции по размещению/отгрузке/ремонту и формату действий.
   > ⚠️ Открытый пункт: точный словарь действий склада в извлечённом тексте статьи не раскрыт. Определяем свой эквивалент (напр. `STORE <item> <shelf>`, `SHIP <item> <shelf>`, `MAINTAIN <shelf>`) и фиксируем в `skills/warehouse.ts` как интерпретацию; при появлении официального кода статьи — синхронизировать.
4. Скоринг: доля валидных действий, совпадающих с детерминированной ground-truth симуляцией.
5. **Критерий готовности:** генератор детерминирован (одинаковый вывод при одинаковом сиде); ручная проверка корректности событий на первых ~20 шагах.

### Фаза 3 — Бейзлайны и оценочный харнесс

1. Реализация рантаймов `prompt`, `memory` (NL-суммаризация отдельным вызовом + окно 3 хода), `stateful` поверх общего ядра.
2. Метрики: точность / средний размер промпта (символы) / суммарные токены — по каждому прогону в `results/`.
3. CLI-прогон матрицы: рантаймы × горизонты {50, 100, 200} × 5 сидов × провайдеры; сводная таблица (статья показывает значимость различий при T≥50, парный t-тест p<0.01).
4. **Критерий готовности:** воспроизводится качественная картина статьи — точность SKILL.state ≥ Stateful при радикально меньших промпте и токенах.

### Фаза 4 — Устойчивость (по «Future work» статьи)

1. Ошибка-в-петле: при исчерпании повторов шаг помечается как невалидный (состояние не тронуто), исполнение продолжается — деградация без разрушения состояния.
2. Для локальных малых моделей: структурированный вывод / JSON-mode / grammar-constrained decoding в Ollama, чтобы убрать 12% синтаксических срывов.
3. Логирование режимов ошибок в разрезе категорий статьи (преждевременная перезапись 68% / типы 20% / синтаксис 12% для open-weight моделей).

## 4. Политика валидации и откатов

Статья фиксирует принцип («невалидный патч → откат-повтор»), но не фиксирует число повторов. Принятая политика:

1. Перед применением `ΔΣ_t` сохраняется снапшот `Σ_t`.
2. При невалидном патче: откат, к промпту добавляется краткое диагностическое сообщение об ошибке валидации, генерация повторяется; **по умолчанию `maxRetries = 3`** (конфигурируемо).
3. По исчерпании повторов: шаг считается невалидным, `Σ_t` не изменяется, действие не выполняется, инцидент пишется в лог с категорией ошибки; цикл продолжается.
4. `R_t` (reasoning) никогда не сохраняется и не попадает в следующий промпт — только `Σ_{t+1}` и новая `O_{t+1}`. Это и даёт 𝒪(1) размер промпта на шаг.

### 09.09.2026 — рантайм обобщён за пределы домена разработки

Ядро, инструменты и хранилище больше не привязаны к схеме дев-задачи: новый домен приносит свой навык, а не правку ядра (описание — §11 INTEGRATION.md).

- **Реестр навыков** (`src/core/skill.ts`, `src/tasks/registry.ts`): `Skill` = схема Σ + доменный guard + процедура P + `initialState` плюс `newPlanItem`/`progress`; запись на диске несёт `skill` и `notation`, а старая запись читается как `dev-task`/`plain`.
- **Корни состояния нескольких проектов** (`src/tasks/projects.ts`): аргумент `project` у всех шести инструментов и `--project` у CLI; достижимы только корни, объявленные пользователем (`--project name=dir` сервера или `STATE3_PROJECTS`), поэтому модель не может направить инструменты в произвольный каталог.
- **Компактная нотация и path-ключи патчей** (`src/tasks/notation.ts`, `src/core/state.ts`): `notation: compact` предписывает писать Σ сжатым псевдокодом, а ключи вида `plan[1].status` и `plan[+]` раскрываются до guard'а и схемы, поэтому доменное правило ими не обходится.
- **Второй встроенный навык `supervise-task`** (`src/tasks/supervise.ts`): Σ супервизора с раундами `assignment → verdict/evidence/feedback`, guard требует `evidence` для `accepted` и `feedback` для `rejected`; общие блоки процедур вынесены в `src/tasks/procedure.ts`.

Проверки: build/typecheck/lint/format:check зелёные, 540 тестов / 26 файлов, `smoke:mcp` 12/12.

### 19.09.2026 — дешёвая правка и проверяемая свежесть (отзывы пользователя)

Три отзыва на dogfood-прогон (`D:\Projects\AgeOfDrift\feedback`: правка тела страницы, сжатие Σ, привязка к коммиту) закрыты; четвёртый (дерево C4, priority medium) оставлен отдельной задачей. Обоснования и границы решений — §14 INTEGRATION.md.

- **Тело страницы правится точечно** (`src/kb/body.ts`; `op patch` / `append` / `history`): три формы правок (`find`/`replace`, `after`/`insert`, `section`/`body`), адрес обязан совпасть ровно один раз, отказ нумерует правку и не меняет ничего; прежние тела хранятся в `page_history` (последние 10) и читаются по `#seq`; отказ схемы называет значение и предел (`issueSizeDetail`).

### 26.09.2026 — state3: имя и дерево задач

Проект переименован в **state3**, а состояние стало древовидным: «задачи будут разделяться, а не в одном state тянуть задачу, которая ещё на очереди». Обоснования и границы решений — §16 INTEGRATION.md.

Перенос отказывается копировать базу, пока рядом лежит `state.db-shm` — её держит живая сессия прежней сборки, а копия из-под пишущего процесса была бы рваной и читалась бы как достоверная. Отказ печатается хуком в stderr, сервером в баннер, CLI одной строкой и `task doctor` как finding; в `readInjection` он возвращается как `unreadable`, а не `none` («здесь ничего нет» — единственный по-настоящему неверный ответ). Вызывается **до** проверки `existsSync(state.db)` в хуке и плагине, иначе переименованный проект читался бы как проект, где состояния никогда не было.
- **Дерево: `parent` и статус `pending`** (`task.parent TEXT REFERENCES task (id) ON DELETE SET NULL`, `INDEX task_parent`, `TASK_STATUSES = pending | active | blocked | done`): `task_start {"parent":…}` отделяет кусок в подзадачу со своей Σ. `SET NULL`, а не `CASCADE`: работа, пережившая декомпозицию, остаётся работой, а сироту видит `doctor` — он же с 27.09.2026 сообщает и петлю в `parent` (§16.22 INTEGRATION.md). Без `pending` три созданные подряд подзадачи все были бы `active`, и прежнее правило «последняя обновлённая открытая задача» отдавало **последнюю созданную** вместо первой по очереди.
- **Порядок очереди — `(created_at, rowid)`**, и `rowid` не избыточен: миллисекундного `created_at` не хватает, потому что агент, дробящий задачу на три части, создаёт все три внутри одной миллисекунды, и без порядка вставки «первый кусок» определялся бы случайным суффиксом id. На этом попался smoke-прогон: обе подзадачи родились в одну миллисекунду, и инъекция взяла вторую — вместе с ней пропала строка `Queued after this`. Правило одно на три места (`queueOrder()` в `store.ts`, `FRONTIER_ORDER`, запрос очереди).
- **Промпт несёт ветку, а не очередь** (`branchLines`, `pickCandidate` в `src/tasks/inject.ts`): кандидат на инжекцию — **фронт работ**, открытая задача, под которой ничего не открыто; поверх Σ листа не больше двух строк — `Branch: <цель корня> [status] -> … -> this task` и `Queued after this: "<цель следующего брата>" (<id>) + N more`, обе **над** Σ. Раздробленная задача — контейнер, её Σ в промпт не попадает: инжекция контейнера вернула бы ровно то, что дробление должно было убрать. Делегированному сабагенту строка очереди не даётся (`queue: false`): ему вручили один кусок, и назвать следующий — значит пригласить его начать самому.
- **Декомпозиция закрывается последней** (`src/tasks/store.ts`): задачу с открытыми подзадачами нельзя перевести в `done` ни `task_patch`, ни `task_finish`; подзадачу нельзя создать под несуществующим или закрытым родителем. Правило живёт в store, а не в guard'е навыка: guard читает одно состояние, а подзадачи — другие строки, и считать надо по строкам (подзадача с неизвестным рантайму скиллом выпадает из `list()`, но родителя держать обязана).
- **Десятого инструмента нет** (поверхность — §16.6): декларации инструментов стоят токенов в каждой сессии, поэтому дерево добавлено в существующие девять — `task_start` получил `parent`, `task_show` — `view: "tree"` (декомпозиция по строке на задачу, без Σ и без процедуры), `task_list` печатает дерево с отступом и счётчиком `(N subtasks, M open)` на родителе. Обход общий (`treeOrder()` в `render.ts`), чтобы CLI и MCP рисовали одно и то же; в CLI добавлены `--parent` и `--tree`. Сирота печатается как корень, не обойдённая из-за цикла задача — плоско в конце: «каждая задача присутствует в списке» — единственное свойство, которое список обязан сохранить при любом виде дерева.

Схема базы выросла до версии 7 (`ALTER TABLE task ADD COLUMN parent`, `CREATE INDEX task_parent`); колонка в `CREATE TABLE task` стоит в конце, как `page.source_commit`, поэтому раскладка свежей базы и базы, дошедшей миграциями, совпадает.
