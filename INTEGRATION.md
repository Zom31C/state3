# План интеграции: SKILL.state в реальные кодинг-агенты

**Цель (подтверждена пользователем 05.09.2026):** довести инструмент до практической пользы — основной класс задач **разработка ПО**, форма применения **интеграция в существующие ИИ-агенты** (Qwen Code, opencode и т.п.), безопасность — **подтверждение опасных действий**.

**Идея:** кодинг-агенты на длинных задачах (рефакторинги, миграции, многофайловые фичи) раздувают транскрипт и теряют прогресс после сжатия/обрыва. Мы даём агенту внешний детерминированный слой состояния Σ из статьи: агент патчит состояние через инструменты, сервер валидирует патчи (модель не может испортить состояние), а компактная Σ инжектируется в контекст и переживает сжатие сессии.

Базовый проект (Фазы 0–4, воспроизведение arXiv:2608.26263) завершён — см. PLAN.md. Этот план — Фазы 5–9.

## 1. Архитектура (три слоя)

```
┌─────────────────────────────────────────────────────────┐
│ Адаптеры агентов                                         │
│  Qwen Code: extension (MCP + UserPromptSubmit hook       │
│             + skill /long-task)                          │
│  opencode:  mcp-конфиг + plugin (compacting hook)        │
│             + AGENTS.md                                  │
├─────────────────────────────────────────────────────────┤
│ MCP-сервер skillstate (переносимое ядро интеграции)      │
│  tools: task_start / task_show / task_patch /            │
│         task_finish / task_list / task_history           │
│         page / search / project_brief                    │
├─────────────────────────────────────────────────────────┤
│ Ядро состояния и базы знаний (Фазы 0–4 + раздел 12)      │
│  DevTaskState zod-схема, mergeState ⊕, guard,            │
│  персистенция .skillstate/state.db (SQLite + FTS5)       │
└─────────────────────────────────────────────────────────┘
```

Принцип: **MCP-сервер — единая точка интеграции** для любого MCP-совместимого агента; адаптеры добавляют лишь (а) инжекцию Σ в контекст и (б) инструкцию P. Сам skillstate **не исполняет побочных действий** (только读写 файлов состояния) — опасные операции исполняет хост-агент через свою систему разрешений.

## 2. Схема состояния дев-задачи (DevTaskState)

Статическая схема на домен «задача разработки» (по статье: одна схема на домен, не на задачу). С 09.09.2026 это **один навык из нескольких**: схема, guard и процедура P упакованы в `devTaskSkill()` (`src/tasks/schema.ts`) и зарегистрированы в реестре навыков (`src/tasks/registry.ts`) рядом с `supervise-task` — обобщение описано в разделе 11.

```jsonc
{
  "goal": "string — задача, одна-две фразы",
  "status": "active | blocked | done",
  "plan": [{ "id": "1", "task": "…", "status": "pending|in_progress|done|skipped", "notes": "…" }],
  "artifacts": { "<путь/файл>": "что изменено, текущий статус" },
  "verifications": [{ "check": "npm test", "status": "pass|fail|pending" }],
  "decisions": ["решение + причина — только то, что нужно будущим шагам"],
  "blockers": ["…"],
  "next": { "action": "конкретный следующий шаг", "risk": "safe|destructive|external" },
}
```

Правила ведения (часть P): хранить только нужное будущим шагам; завершённое сжимать до результата; `null` удаляет ключ; после каждого значимого шага — `task_patch`.

Guard домена (детерминированный): плановый элемент нельзя вернуть из `done` в `pending` без явной пометки в notes (аналог «преждевременной перезаписи» из статьи); `status: done` задачи нельзя снять без архивации.

## 3. MCP-сервер (Фаза 6)

- Стек: `@modelcontextprotocol/sdk` (TypeScript, stdio-транспорт), запуск `node dist/mcp/server.js` (или `npx tsx src/mcp/server.ts` в dev).
- Каталог состояния: `.skillstate/` в корне проекта (git-игнорируется по желанию), в нём один файл `state.db` (SQLite, WAL): задачи, история патчей (аудит), страницы базы знаний и связи между ними. Атомарность — транзакцией; легаси-корень из `<id>.json`/`<id>.history.jsonl` переносится подкомандой `task migrate` (раздел 12).
- Инструменты:
  | Tool            | Аргументы                     | Поведение                                                                                                                               |
  | --------------- | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
  | `task_start`    | `goal`, `plan?`               | создаёт задачу, возвращает компактную Σ + краткую P-инструкцию                                                                          |
  | `task_show`     | `id?` (по умолчанию активная) | компактная Σ (JSON без пробелов) + P-напоминание                                                                                        |
  | `task_patch`    | `patch`                       | валидация (zod + guard) → mergeState ⊕ → атомарная запись; при ошибке — диагностическое сообщение (агент ретраит, состояние не тронуто) |
  | `task_finish`   | `summary`                     | status=done, архивирует                                                                                                                 |
  | `task_list`     | —                             | все задачи проекта со статусами                                                                                                         |
  | `task_history`  | `id`, `limit?`                | последние патчи (аудит/откат вручную)                                                                                                   |
  | `project_brief` | —                             | карта базы знаний: по строке на страницу, в бюджете 4000 символов и без тел (§12.7)                                                     |
  | `page`          | `op` и аргументы операции     | база знаний: `get`/`put`/`list`/`delete`/`init`/`link`/`unlink`/`links` (§12.4–12.5)                                                    |
  | `search`        | `query`, `kind?`, `limit?`    | полнотекстовый поиск по задачам и страницам, совпадения со сниппетами (§12.6)                                                           |
- Активная задача одна на проект (последняя `active`); `task_show`/`task_patch` без id работают с ней.
- Дополнение от 09.09.2026 (раздел 11): у всех шести инструментов появился необязательный аргумент `project` (имя объявленного корня состояния), у `task_start` — ещё `skill` и `notation`, а `task_list` дописывает строки возможностей `skills: …` и `projects: …`.
- Дополнение от 12.09.2026 (раздел 12): инструментов **девять** — к шести `task_*` добавились `project_brief`, `page` и `search`. Все три принимают тот же аргумент `project`, поэтому супервизор читает базу знаний рабочего проекта так же, как его Σ.

## 4. Адаптер Qwen Code (Фаза 7)

Упаковка — **Qwen Code extension** (bundled-механизм: расширения поддерживают QWEN.md-контекст, commands, skills, agents, MCP-серверы, settings, hooks):

1. **MCP-сервер** из Фазы 6 в манифесте расширения.
2. **UserPromptSubmit hook**: если есть активная задача — добавляет в контекст каждого хода блок `## Active task state (skillstate)` с компактной Σ (аналог промпта A.4: модель видит состояние, а не транскрипт). На `SessionStart` к нему добавляется блок `## Project brief (skillstate)` — карта базы знаний проекта (§12.7): старт сессии — единственный момент, когда транскрипт ещё пуст и ориентироваться не по чему.
3. **Skill `/long-task`**: инструкция P — когда начинать задачу, как вести Σ, что после каждого значимого шага нужен `task_patch`, что `next.risk: destructive|external` требует подтверждения пользователя до исполнения.
4. Локальная установка/проверка — через механизм link/test расширений (см. bundled skill `extension-creator`).

## 5. Адаптер opencode (Фаза 8)

Проверено по docs (05.09.2026):

- **MCP**: `opencode.json`/`opencode.jsonc` (проект или глобально), верхний ключ `mcp`:
  ```jsonc
  {
    "$schema": "https://opencode.ai/config.json",
    "mcp": {
      "skillstate": {
        "type": "local",
        "command": ["node", "<путь>/dist/mcp/server.js"],
        "enabled": true,
      },
    },
  }
  ```
- **Plugin**: JS/TS-модуль в `.opencode/plugins/` (проект) или `~/.config/opencode/plugins/` (глобально); типизация `@opencode-ai/plugin@1.18.26` — именованный экспорт асинхронной функции `(input: PluginInput) => Promise<Hooks>`, где `input = {client, project, directory, worktree, experimental_workspace, serverUrl, $}`. Реализованные хуки:
  - `experimental.session.compacting(input, output)` — **инжекция Σ в контекст сжатия**: `output.context.push(...)` с текущим состоянием задачи → прогресс переживает compaction (документированный паттерн «Include any state that should persist across compaction»).
  - `experimental.chat.system.transform(input, output)` — `output.system.push(Σ)`: компактная Σ в системном промпте каждого запроса. Присутствует в типах 1.18.26, в публичной документации не описан; проверен живым прогоном — модель цитирует `goal` из Σ без единого вызова инструмента.
  - `tool.execute.before` — opt-in guard (`SKILLSTATE_GUARD=1`): `throw` отменяет вызов `bash`/`write`/`edit`/`patch`, если `next.risk` активной задачи `destructive` или `external`.
- **AGENTS.md**: блок P-инструкций (тот же текст, что skill `/long-task`); инструменты MCP видны агенту как `skillstate_task_*`.
- **Каталог проекта**: opencode передаёт `worktree: "/"`, когда проект не является git-репозиторием (`project.id === "global"`), а Bun считает `"/"` абсолютным путём. Плагин отбрасывает корни ФС, предпочитает `directory` и выбирает тот каталог, где уже лежит `.skillstate/`.

## 6. Безопасность (подтверждение опасных действий)

1. skillstate сам не исполняет shell/HTTP/правки — только файлы `.skillstate/` (невредимо).
2. `next.risk: safe|destructive|external` в Σ; инструкция P **требует** запросить подтверждение пользователя перед исполнением destructive/external.
3. Хост-агент обеспечивает второй уровень: approval-режимы Qwen Code, permission-система opencode (`permission.asked/replied`).
4. Опционально (Фаза 8): opencode-plugin `tool.execute.before` блокирует bash/write, если активная задача имеет неподтверждённый destructive-next.

## 8. Критерии успеха

1. В Qwen Code и opencode агент ведёт дев-задачу через `task_*`; состояние хранится в `.skillstate/`, патчи валидируются сервером.
2. После сжатия сессии (`/compact` в Qwen Code, compaction в opencode) или перезапуска агент **восстанавливает прогресс из Σ без потерь** — главный практический выигрыш.
3. Невалидный патч никогда не портит файл состояния; история патчей аудиторна.
4. Опасные действия помечены `next.risk` и исполняются только после подтверждения (инструкция P + permission-система хоста).
5. Все проверки проекта зелёные (typecheck/lint/тесты), новые модули покрыты тестами.

## 9. Проверенные факты об интеграционных поверхностях (05.09.2026)

- **Qwen Code** (проверено 05.09.2026 по живой установке **0.22.3** — `qwen --version`: `lib/bundled/extension-creator/SKILL.md`, `lib/bundled/qc-helper/docs/**`, `lib/examples/{mcp-server,starter,skills}/`, `lib/chunks/*`; в кэше обновлений лежит также копия 0.21.6, и более ранние пометки «0.21.6» в этом документе относились к ней):
  - манифест — `qwen-extension.json` в корне расширения (без точки в начале); поля: `name`, `version`, `displayName`, `description`, `contextFileName` (по умолчанию `QWEN.md`), `mcpServers`, `settings` (запросы env-переменных), `hooks`, `channels`, `lspServers`;
  - path-переменные `${extensionPath}`, `${workspacePath}`, `${/}` гидратируются в полях `command`, `args`, `cwd`, `env`, `headers`, `url`, `trust` у `mcpServers` и в `command` inline-хуков; в file-based `hooks/hooks.json` подставляется только `${CLAUDE_PLUGIN_ROOT}`. **`${workspacePath}` — это каталог запуска `qwen`** (`targetDir`/`workingDirectory`), а не каталог проекта, подключённого к сессии; `${workspaceFolder}` не поддерживается и раскрывается в пустую строку (проверено: сервер с таким `cwd` не стартует — `Disconnected`);
  - окружение дочернего процесса MCP-сервера = окружение хоста плюс `env` из манифеста. Хост передаёт `QWEN_CODE=1`, `QWEN_CODE_SESSION_ID`, `QWEN_CODE_MODEL`, `QWEN_CODE_PROJECT_DIR` и др.; **`QWEN_CODE_PROJECT_DIR` — это служебный каталог данных `~/.qwen/projects/<slug от каталога запуска>`**, а не каталог исходников проекта, поэтому как корень состояния непригоден (измерено временным зондом);
  - хуки: тип `command` получает JSON в stdin — документированные общие поля `session_id`, `transcript_path`, `cwd`, `hook_event_name`, `timestamp` плюс поля события (у сабагентов также `agent_id`/`agent_type`); **семантика `cwd` в документации не определена** (каталог запуска или каталог сессии). Хук возвращает JSON в stdout (`hookSpecificOutput.additionalContext`); exit 0 — успех, exit 2 — блокирующая ошибка (stderr уходит модели), прочие коды — неблокирующие; `timeout` в **миллисекундах**; у `UserPromptSubmit` нет `matcher`, у `SessionStart` matcher — по источнику (`startup|resume|clear|compact`), есть также `PreCompact`/`PostCompact`;
  - инжектированный контекст попадает в ход обёрнутым в `<qwen:user-prompt-submit-context>`;
  - ресурсы: `skills/<name>/SKILL.md` (frontmatter `name`, `description`, `argument-hint`), `commands/<name>.md` (подкаталог → `/ns:name`), `agents/<name>.md`, `QWEN.md`;
  - установка: `qwen extensions new|link|install|list|uninstall|settings`; `link` создаёт symlink (правки подхватываются), после подключения нужен перезапуск сессии;
  - **`/cd` и `/reload-plugins` не пересоздают дочерний процесс MCP-сервера расширения** (измерено 09.09.2026): `/cd <dir>` меняет каталог сессии — inline-хуки сразу начинают читать Σ нового каталога, — но сервер остаётся с тем `cwd`, который получил при старте; `/reload-plugins` («Reload extension changes (commands, skills, agents, hooks, MCP/LSP servers) from disk») процесс тоже не перезапускает: pid и время его старта не изменились ни после `/cd`, ни после `/reload-plugins`. Единственное исправление — запуск `qwen` из каталога проекта либо `SKILLSTATE_STATE_DIR`;
  - **живой сервер расширения держит в памяти старый скомпилированный код** (измерено 09.09.2026): после `npm run build` уже запущенная сессия Qwen Code продолжала отвергать path-ключи (`{"plan[1].status":"done"}`) как `unknown-key`, тогда как CLI проекта с тем же `dist` их принимал. Причина та же, что и у пункта выше: лаунчер расширения один раз делает `import` `dist/mcp/server.js` при старте дочернего процесса, и ни `/cd`, ни `/reload-plugins` процесс не пересоздают. Помогает только перезапуск `qwen`;
  - проверка: `qwen mcp list` (статус `Connected`), диалог `/mcp`, `qwen --debug` (лог `[TRUSTED_HOOKS]`, `[SKILL_LOAD]`, `[MCP]`), `QWEN_DEBUG_LOG_FILE`;
  - `~/.qwen/tmp/<hash>/logs.json` — **персистентная история пользовательских промптов** (не лог одной сессии): по ней можно восстановить, какие команды (`/cd`, `/compact`, `/reload-plugins`) и когда выполнял пользователь, в том числе в прошлых сессиях;
  - MCP-инструменты в сессии видны как `mcp__<server>__<tool>`.
- **opencode** (1.18.26): MCP — ключ `mcp` в `opencode.json(c)`, `type: "local"`, `command: [...]`, опции `cwd/environment/enabled/timeout` (docs/mcp-servers). Плагины — `.opencode/plugins/` или `~/.config/opencode/plugins/`, `PluginInput = {client, project, directory, worktree, experimental_workspace, serverUrl, $}`; хуки: `experimental.session.compacting` (инжекция в промпт сжатия), `experimental.chat.system.transform` (`output.system.push` — инжекция в системный промпт каждого запроса; присутствует в типах, но не в публичной документации), `tool.execute.before/after` (`throw` отменяет вызов), `session.*`, `message.*`, `permission.*`, `todo.updated`, `tui.prompt.append` и др. Проект без git-репозитория даёт `project.id === "global"` и `worktree: "/"`.
- **Локальная модель как провайдер Qwen Code** (измерено 09.09.2026, RTX 3090 24 GiB VRAM / 16 GiB RAM, i7-10700K): LM Studio на `127.0.0.1:1234/v1`, модель `qwen/qwen3.8-27b` Q4_K_M (веса 16.52 GiB, GGUF допускает ctx до 262144). Загрузка при ctx 65536 / 73728 / 81920 / 131072 занимает практически одинаковые ~24.2 GiB VRAM (загрузчик насыщает видеопамять независимо от длины контекста), зато растёт расход системной RAM: свободная падает с 1.4 GiB до 0.42 GiB — KV-кэш частично уходит туда. `lms load --estimate-only` для оценки непригоден: не учитывает KV-кэш (одинаковые 16.52 GiB при любом ctx, `Confidence: LOW`). Итог: ctx **81920** — и в LM Studio (`lms load qwen/qwen3.8-27b -c 81920 -y`), и в `generationConfig.contextWindowSize` провайдера в `~/.qwen/settings.json`. Значения обязаны совпадать: если лимит хоста больше загруженного контекста, длинные запросы упираются в реальное `loaded_context_length` (видно в `GET /api/v0/models`). Перезагрузка модели через CLI не сохраняется как конфигурация по умолчанию — после перезагрузки LM Studio контекст нужно задать снова (либо в UI, либо тем же `lms load`).
- **Общее**: оба агента — MCP-хосты ⇒ ядро интеграции (MCP-сервер) пишется один раз.

## 11. Обобщение рантайма: навыки, проекты, нотация, path-патчи (09.09.2026)

Фазы 5–9 строили ядро вокруг одного домена. Четыре обобщения ниже делают рантайм, инструменты и хранилище доменно-нейтральными: новый домен приносит свой навык, а не правку ядра. Все четыре реализованы и покрыты тестами.

### 11.1 Реестр навыков

Навык — это Σ-схема + доменный guard + текст процедуры P + `initialState`. Интерфейс `Skill` (`src/core/skill.ts`):

| Поле                        | Назначение                                                         |
| --------------------------- | ------------------------------------------------------------------ |
| `name`                      | имя навыка; попадает в запись на диске и в вывод инструментов      |
| `schema`                    | схема Σ (strict: неизвестные ключи отклоняются)                    |
| `guard?`                    | доменные правила; проверяются до схемы                             |
| `instructions`              | процедура P этого навыка                                           |
| `initialState`              | Σ₀ — обязана проходить схему                                       |
| `newPlanItem?(task, index)` | как строка шага становится элементом плана: форму определяет домен |
| `progress?(state)`          | счётчики `done`/`total` для списков; без него — 0/0                |

Реестр — `src/tasks/registry.ts`: `createSkillRegistry(skills, defaultName)`, `builtinSkills()`, `builtinSkillRegistry()`, `DEFAULT_SKILL_NAME = 'dev-task'`. Встроенных навыков два: `dev-task` (`src/tasks/schema.ts`) и `supervise-task` (`src/tasks/supervise.ts`).

Запись задачи (тогда — файл `.skillstate/<id>.json`, с 12.09.2026 — строка таблицы `task` в `.skillstate/state.db`, раздел 12) несёт поля `skill` и `notation`:

- запись без них (написанную прежним рантаймом) читают как `dev-task` / `plain` и нормализуют при следующей записи — проверено на реальной записи от 07.09.2026;
- запись с именем навыка, которого у рантайма нет: `show`/`patch` бросают ошибку категории `skill` с перечислением доступных навыков, а `list` пропускает её молча — чужая или повреждённая запись не должна ломать список.

`TaskStore.finish()` один на все навыки, потому что любая Σ несёт одинаковый контракт завершения: `status`, append-only массив `decisions` и `next {action, risk}`.

Тексты процедур собираются из общих блоков `src/tasks/procedure.ts` (`RISK_RULES`, `PATCH_SEMANTICS`, `STATE_HYGIENE`, `composeProcedure`), поэтому семантика слияния и таксономия рисков имеют один источник истины для обоих навыков.

### 11.2 Корни состояния нескольких проектов

Все шесть MCP-инструментов принимают необязательный аргумент `project`; CLI — флаг `--project <name>` (вместо `--root`, который с ним несовместим).

Корни **объявляются заранее, и достижимы только объявленные**:

- сервер: `--project name=dir` (повторяемый) — `src/mcp/server.ts`;
- окружение: `SKILLSTATE_PROJECTS` = `name=dir;name2=dir2` (разделитель `;` или перевод строки) либо JSON-объект `{"name":"dir"}` — `parseProjectsSpec` (`src/tasks/projects.ts`);
- имя проекта обязано соответствовать `/^[a-z0-9][a-z0-9_-]{0,63}$/`; относительный каталог разрешается против cwd; повтор имени — ошибка.

Это и есть аргумент безопасности: объявление приходит из окружения пользователя или конфигурации хоста и никогда от модели, а модель выбирает только **имя** из объявленного списка. Направить инструменты в произвольный каталог — прочитать его или записать в него — она не может.

Неизвестное имя даёт ошибку с перечислением объявленных корней. Проверено: `unknown project "nope" — declared: racegame (D:\Projects\RaceGame\.skillstate)`.

`task_list` дописывает строки возможностей `skills: …` и `projects: …`, чтобы модель узнавала, что существует, без отдельного инструмента.

Хук Qwen Code (`extensions/skillstate/hooks/inject-state.mjs`) при заданной `SKILLSTATE_PROJECTS` инжектирует также активную задачу каждого объявленного проекта — блоком `## Supervised projects (skillstate)` с подзаголовком `### <name> — <rootDir>` и теми же строками Σ, что и для основной задачи (заголовок с навыком, однострочная Σ, напоминание компактной нотации, подсказка о размере). Подробности поведения, считанные из файла хука:

- корень, совпадающий с основным, пропускается (на Windows сравнение без учёта регистра), чтобы Σ не инжектировалась дважды;
- нечитаемый корень и проект без активной задачи пропускаются, не скрывая остальные;
- некорректное объявление (`SKILLSTATE_PROJECTS` не разбирается) отключает всю секцию: хук не имеет права ронять ход;
- секция заканчивается подсказкой `Patch these with the project argument: task_patch {"project":"<name>", …}.`

Целевой сценарий: одна супервизирующая сессия читает и патчит состояние рабочего агента, запущенного в другом каталоге проекта.

### 11.3 Компактная нотация и дешёвые path-патчи

**Нотация** (`src/tasks/notation.ts`) — свойство задачи: `plain` (по умолчанию) или `compact`. Для `compact` к процедуре P добавляется блок с требованием писать значения Σ как сжатый псевдокод: без артиклей и вводных слов, символы `->` `+` `-` `=` `!` `?`, одна запись — одна строка, пути, идентификаторы, команды, тексты ошибок и числа дословно, и никогда не сжимать ограничение, причину или падающую команду. Основание: Σ реинжектируется каждый ход, поэтому её размер — повторяющаяся стоимость; сильнее всего это важно для локальных моделей с небольшим контекстом (замер потолка — раздел 9). `renderTaskHead` печатает для compact-задачи однострочное напоминание, поэтому хосты, инжектирующие Σ без P (хуки, адаптеры), тоже его получают.

**Path-ключи патча** адресуют один элемент массива:

```json
{
  "plan[1].status": "done",
  "rounds[0].verdict": "accepted",
  "decisions[+]": "…",
  "plan[+]": { "id": "3", "task": "…" }
}
```

Индексы с нуля, `[+]` — добавление в конец. Ниже элемента можно адресовать и вложенные ключи: недостающие объекты создаются (`assignAtTail`), что покрыто тестами ядра, хотя у обоих встроенных навыков элементы массивов плоские. Реализация — `expandPathPatch(state, patch)` в `src/core/state.ts`: она переписывает path-ключи в обычный патч «массив целиком» **до** guard'а и валидации схемы, поэтому path-ключ не может обойти доменное правило. Тест это фиксирует (`tests/tasks/store.test.ts`): переоткрытие `done`-пункта плана path-ключом отклоняется guard'ом, а тот же патч вместе с непустым `plan[0].notes` проходит.

Адресуемы только массивы: обычные объекты и так сливаются рекурсивно, а точечные ключи над ними неоднозначны, потому что ключи `artifacts` — это пути файлов (`artifacts.INTEGRATION.md`).

Ограничения, у каждого своё сообщение и категория `path`: индекс вне диапазона (сообщение указывает на `field[+]`), путь в поле-не-массив, `null` на элемент или на `[+]` (удаление path-ключом невыразимо — пришлите массив без этого элемента), ключи ниже `[+]`, путь в элемент-не-объект, и одно поле одновременно целиком и path-ключом в одном патче.

История пишет патч **как он был отправлен** (с path-ключами), а не его раскрытие: аудит показывает, что запросил агент и во сколько символов это обошлось.

### 11.4 Второй встроенный навык: `supervise-task`

Σ (`src/tasks/supervise.ts`): `{ goal, status, spec, worker, rounds: [{ id, assignment, verdict, evidence, feedback }], decisions, blockers, next }`, где `verdict` — `pending` | `accepted` | `rejected`. Прогресс в списках — принятые раунды ко всем. Навык объявлен без `newPlanItem`, поэтому `task_start` с планом для него отклоняется: `skill "supervise-task" takes no plan; start it with a goal, then patch the fields task_show lists`.

Guard: завершённую задачу нельзя переоткрыть; `blocked` требует хотя бы один блокер; `accepted` требует непустого `evidence`; `rejected` требует непустого `feedback`; одновременно может быть не более одного `pending`-раунда.

P описывает цикл: одно задание → рабочий агент его исполняет → супервизор проверяет результат сам (читает файлы, запускает проверки, никогда не принимает на слово рабочего) → вердикт и `evidence`, при отказе — `feedback`, по которому рабочий исправит без догадок → следующее задание. Там же зафиксировано, что запуск рабочего внутри его собственного проекта — `safe`, а правка конфигурации пользователя, глобальная установка и любая публикация — `external`.

### 11.6 Словарь отказов: один источник на трёх потребителей (10.09.2026)

Категории отказа записи жили в четырёх копиях: тип `ValidationErrorCategory` в `src/core/validator.ts` (четыре значения), `TaskPatchError.category: string` в `src/tasks/store.ts` (который бросал ещё `path`, `skill` и `notation`), `switch` подсказок в `src/mcp/tools.ts` и список в тексте процедуры P. Попутно тест вскрыл тонкость zod: значение не из `enum` она относит к `invalid_value`, поэтому `type-coercion` достижим только на не-enum полях.

### 11.7 Заблокированная задача остаётся открытой (10.09.2026)

`status: "blocked"` делал задачу невидимой для всех инструментов, вызванных без `id`: `TaskStore.activeId()` искал ровно `status === 'active'`, поэтому `task_show`, `task_patch`, `task_finish` и `task_history` отвечали `No active task found`. Тот же фильтр был в хуке расширения (`pickActive` в `extensions/skillstate/hooks/inject-state.mjs`), из-за чего Σ заблокированной задачи не инжектировалась в контекст — то есть исчезала ровно в той сессии, которая должна её разблокировать после `/compact`. Дефект найден эмпирически: задача этой супервизии была переведена в `blocked` и потеряла доступ к собственному состоянию.

Исправление в обоих слоях одинаковое: открытой считается задача не в `done`, при этом `active` имеет приоритет над `blocked`, поэтому поведение сессии с одной активной задачей не меняется. `activeId()` возвращает самую свежую по `updatedAt` (список уже отсортирован), хук выбирает по тому же признаку. Проверено тестами (`tests/tasks/store.test.ts`: заблокированная задача находится и патчится без `id`, активная побеждает заблокированную) и прогоном хука на реальной `blocked`-задаче: Σ инжектируется с пометкой `(blocked)`.

Метрики: build/typecheck/lint/format:check зелёные, 551 тест / 27 файлов, прогон хука на `blocked`-задаче даёт `additionalContext` с её Σ.

### 11.9 `null`-удаление несуществующего ключа больше не проходит молча (11.09.2026)

Дефект найден эмпирически на собственной Σ: сжимая `artifacts`, супервизор отправил `{"artifacts.src/": null}`, полагая, что ключи объекта адресуются через точку так же, как элементы массива. `PATH_KEY` распознаёт только поля-массивы, поэтому ключ остался обычным полем верхнего уровня со значением `null`; `mergeState` выполняет `delete result[key]` **до** валидации, а удаление отсутствующего ключа — ничто. Строгая схема (`z.strictObject`) не увидела чужого поля, и патч ответил `Patched`, оставив в Σ ровно ту запись, которую агент считал удалённой. Это худший класс отказа: состояние расходится с убеждением агента, и расходится молча.

Исправление — `findMalformedDeleteKeys(patch)` в `src/core/state.ts`: синтаксический фильтр по ключам верхнего уровня (значение `null`, ключ не парсится как path-ключ и содержит `.` или `[`). `validatePatch` сообщает их до слияния как категорию `unknown-key`, называя ключ и две законные формы: path-ключ для поля-массива и вложенный словарь для ключей объекта. Дополнительно `assignAtTail` отклоняет `null` по leaf-ключу, которого у элемента массива нет (категория `path`), поэтому опечатка `plan[0].note` тоже не проходит незамеченной.

Граница правила выбрана намеренно: удаление **плоского** отсутствующего ключа остаётся законным. В навыке `warehouse` «пустая полка» означает «ключа нет в Σ» (поля схемы `.optional()`, SHIP/MAINTAIN удаляют ключ), поэтому `MAINTAIN` по уже пустой полке обязан принимать `{shelf_7: null}`. Первая версия проверки отвергала именно это и ломала `tests/matrix.test.ts` (`judged` = 3 вместо 4) — регрессия и задала окончательную формулировку. Проверить «известно ли схеме это поле» нельзя: `StateSchema` намеренно открывает только `safeParse`, ядро не знает про zod, поэтому проверка синтаксическая и от навыка ничего не требует.

Метрики: build/typecheck/lint/format:check зелёные, 583 теста / 29 файлов (+9: `findMalformedDeleteKeys` 5, `expandPathPatch` 1, `validatePatch` 2, `TaskStore.patch` 1); `matrix` снова зелёный.

## 12. Единая база состояния и база знаний проекта (11–12.09.2026)

Фазы 5–9 решали одну половину задачи: прогресс **текущей** задачи переживает сжатие сессии. Вторая половина — знания **проекта**: что это за проект, чего от него хочет пользователь, как в нём начинать работу, что делает каждая фича и почему решения приняты так, а не иначе. Без неё каждая новая сессия начинает с нуля и задаёт пользователю вопросы, на которые проект уже ответил, а ответы живут в транскрипте, который сжимается и теряется.

Обе половины легли в один файл — `.skillstate/state.db` (SQLite): задачи и страницы ищутся одним полнотекстовым индексом и связываются друг с другом рёбрами. Модель — «Jira + Confluence для LLM», с той разницей, что читатель один и платит токенами, поэтому у данных три уровня детализации (§12.5), а у «вводного гайда» — жёсткий бюджет (§12.7).

### 12.1 Один файл состояния вместо набора JSON

`.skillstate/state.db`: `better-sqlite3` 12.11.1 (prebuild под Node 20.18.1/win-x64; `node:sqlite` на этой версии недоступен), журнал WAL, версия схемы в таблице `meta` (`SCHEMA_VERSION = 1`). Таблицы: `task`, `task_history`, `page`, `link`, `search` (виртуальная FTS5-таблица, синхронизируемая триггерами с `page` и `task`).

Слой `src/db/`: `schema.ts` (DDL и версия), `database.ts` (порт `SqlDatabase`, `openStateDatabase(path, {readOnly|mustExist|noMkdir})`, `ensureSchema`, `checkpoint`). Порт нужен, чтобы сторы не знали про драйвер: тесты подменяют его, а рантайм открывает одно соединение на корень.

`TaskStore` переведён на базу без изменения публичного контракта — те же `start`/`show`/`patch`/`finish`/`list`/`history`, та же валидация патча до записи; изменился только `meta.path` (теперь это `state.db`) и способ хранения: запись задачи и её история пишутся одной транзакцией, соединение открывается лениво и закрывается владельцем (сервер закрывает все созданные сторы при выходе, поэтому WAL сворачивается и корень остаётся одним файлом).

### 12.2 Миграция легаси-корней и диагностика

- `npm run run -- task migrate` — переносит `<id>.json` и `<id>.history.jsonl` в `state.db`; легаси-файлы **архивируются**, а не удаляются (`--purge` — удалить вместо архива). Записи переносятся дословно: миграция не имеет права переинтерпретировать чужую Σ.
- `npm run run -- task doctor` — отчёт о корне: `PRAGMA integrity_check`, версия схемы, счётчики задач/истории/страниц/связей, нечитаемые строки и **висячие рёбра** (связь, у которой нет одного из концов, — см. §12.4).

Обе подкоманды работают с самим корнем, а не с активной задачей, поэтому `migrate` и `doctor` не требуют открывать стор задач обычным путём. Живой корень этого проекта мигрирован: 4 задачи и 79 записей истории на момент переноса; `doctor` после миграции — schema v1, integrity ok. Повторный `doctor` 12.09.2026: tasks 4, history 88 (аудит пополняется каждым патчем), pages 0, links 0, indexed 4.

### 12.3 Хук читает базу (дефект, найденный по ходу)

Хук `inject-state.mjs` — второй потребитель состояния, и он срабатывает на **каждом** промпте. После перевода стора на базу он продолжал читать JSON-файлы, то есть расширение молча теряло Σ в каждом мигрированном проекте: инструменты работали, а инжекции не было. В плане этого пункта не было — найден при обходе потребителей хранилища.

Исправление: компилируемая половина чтения вынесена в `src/tasks/inject.ts` (`readInjection(rootDir, options)`), хук находит её через `extensions/skillstate/lib/home.mjs` (общее для сервера и хука разрешение сборки: `SKILLSTATE_HOME` → обход каталогов вверх по маркерным файлам) и вызывает из `dist/tasks/inject.js`. Легаси-JSON остался фолбэком для корня без базы — немигрированный проект продолжает работать.

Два решения, принятых после замеров, а не по вкусу:

- ридер открывается `{mustExist: true}`, **не** `readOnly`: зонд показал, что read-only-соединение не удаляет `-wal`/`-shm` при закрытии, поэтому хук оставлял бы два лишних файла в корне на каждом промпте;
- корень со `state.db` **авторитетен**: лежащий рядом легаси-JSON не читается, потому что миграция его архивировала и фолбэк инжектировал бы устаревшую Σ. Нечитаемая база даёт строку в stderr и пустой stdout — ход не блокируется, но пропажа Σ больше не тихая.

Тот же обход потребителей нашёл вторую половину того же дефекта — и уже в адаптере, которого план не касался. Плагин opencode (`adapters/opencode/plugin/skillstate.js`) перебирал только `*.json` в корне состояния, поэтому в мигрированном проекте не находил ни одной записи: Σ молча исчезала из контекста, а opt-in guard (`SKILLSTATE_GUARD=1`) терял `next.risk` и переставал блокировать опасные вызовы — то есть ломалась не только инжекция, но и слой безопасности. Подтверждено 12.09.2026 на живом корне: `--self-test` плагина отвечал `no active task in D:\Projects\skillState\.skillstate`, тогда как хук Qwen Code на том же каталоге печатал Σ активной задачи.

Закрыто тем же днём по тому же образцу: плагин находит сборку (`SKILLSTATE_HOME` → обход каталогов вверх от своего файла, маркер `dist/tasks/inject.js`) и зовёт `readInjection`, а легаси-JSON остаётся путём для корня без базы. Ради guard'а `readInjection` возвращает теперь и `next.risk` задачи, пропущенный через словарь `RISK_LEVELS`: уровень риска обязан приходить из того же чтения, что и текст, иначе два запроса к одной базе могут разойтись, и host будет блокировать вызовы не по тому состоянию, которое показал модели. Цена — автономность файла стала частичной: копия в `.opencode/plugins/` без `SKILLSTATE_HOME` сборку не найдёт и напишет в лог `warn` вместо Σ (молча ничего не пропадает). Бриф плагин вводит на первом запросе сессии и при сжатии: события «старт сессии» у opencode нет, поэтому ключ — `sessionID` из аргумента хука, а без него — один раз на процесс. Проверка в `smoke:mcp` (плагин запускается на настоящей базе и печатает Σ вместе с брифом) и на живом корне: self-test снова печатает Σ.

### 12.4 База знаний: страницы и связи

Страница (`src/kb/schema.ts`): `id` (`/^[a-z0-9][a-z0-9_-]{0,63}$/`), `kind`, `title` (≤200), `summary` (≤200), `body` (≤20000), `parent`, `status` (`current|stale|archived`), `pin`, `createdAt`/`updatedAt`. Видов шесть: три **синглтона** — `project` (что за проект, стек, команды), `user-intent` (чего хочет пользователь, что вне scope), `onboarding` (как начинать работу) — их `id` равен виду, и повторяемые `feature`, `decision`, `note`.

`pageGuard` отклоняет до записи: синглтон под чужим id, несуществующего родителя, цикл в `parent` и глубину вложенности больше `PARENT_DEPTH_LIMIT` (100). Отказ несёт категорию из общего словаря (§11.6), поэтому `KbError` и `TaskPatchError` говорят с агентом на одном языке.

`PageStore.put` — create-or-update: пропущенное поле сохраняет прежнее значение, `parent: null` сбрасывает родителя. `delete` в той же транзакции убирает рёбра страницы, а её дети становятся корневыми (ответ перечисляет их: молчаливое переподвешивание — способ потерять дерево).

Связи (`src/kb/links.ts`) полиморфны: концы задаются как `page:<id>` или `task:<id>`, поэтому задача и страница связываются одним ребром с именем `rel` (`documents`, `implements`, `decides`, …). Внешний ключ на такой конец не поставить — значит висячее ребро возможно, и его считает поломкой `doctor`; создаётся ребро только между существующими объектами одного корня. Смысл связей для агента: от страницы фичи видно задачу, которая её сделала, а от задачи — что о ней написано.

### 12.5 Три инструмента вместо тридцати: `page`, `search`, `project_brief`

Инструментов по-прежнему **девять**: шесть `task_*` плюс три новых. Декларации инструментов стоят токенов в каждой сессии, поэтому `page` — один инструмент с аргументом `op` (`get`, `put`, `list`, `delete`, `init`, `link`, `unlink`, `links`), а не восемь отдельных; аргументы, которых операция не принимает, отклоняются (`op "get" does not take "summary"`), а не игнорируются.

Уровни детализации — ответ на «сколько стоит ориентирование»:

| Уровень | Что отдаёт                                     | Цена                            |
| ------- | ---------------------------------------------- | ------------------------------- |
| L0      | `project_brief` — по строке на страницу        | ≤4000 символов, тел нет вовсе   |
| L1      | `page get` / `task_show` — объект целиком      | одна страница или одна Σ        |
| L2      | `search` — совпадения со сниппетами ≈120 симв. | ≤50 совпадений, по умолчанию 10 |

Порядок чтения для агента без контекста: L0 → `search` → L1. Он же записан в шаблоне `onboarding` (§12.7).

### 12.6 Поиск: FTS5 с LIKE-фолбэком

`search` (`src/kb/search.ts`) ищет по задачам и страницам одним запросом: FTS5 `unicode61` по `title`/`summary`/`body` с весами bm25 10/5/1 (заголовок важнее тела), аргумент `kind` сужает до задач или страниц.

Запрос приходит от модели, поэтому он не должен уметь сломать MATCH: каждое слово кавычится в фразу и слова соединяются implicit AND — синтаксис FTS5 (`OR`, `*`, `NEAR`, `column:`) из запроса недостижим. При нуле совпадений или ошибке MATCH выполняется LIKE-скан подстроки: частичное слово и опечатка дают ответ, а не пустоту.

### 12.7 Холодный старт: бриф, шаблоны, вводный гайд

**Бриф** (`src/kb/brief.ts`) — L0 в жёстком бюджете 4000 символов. Режется целыми строками сверху вниз по приоритету (синглтоны → `pin` → `feature`/`decision`/`note`, внутри группы свежие выше) и никогда не пополам: обрезанное сообщается строкой `N more page(s)` и подсказкой `page list`, `archived` исключены, но их счётчик виден. Тест фиксирует главное свойство: бриф одинаков при пустом теле и при теле в 20000 символов — то есть стоимость ориентирования не зависит от того, насколько проект документирован.

**Хук вводит тот же бриф** секцией `## Project brief (skillstate)` после Σ — и **только на `SessionStart`, только для основного корня**. На промпте сессия бриф уже видела, и повтор стал бы налогом на каждый ход; у супервайзера он умножался бы на число объявленных проектов, которым достаточно `project_brief {"project":"<name>"}`. Пустая база не брифуется вовсе (`renderDatabaseBrief` возвращает `null`): иначе «страниц ещё нет» печаталось бы на старте каждой сессии каждого такого проекта, тогда как инструмент в том же случае отвечает развёрнуто и предлагает `init`.

**`page {"op":"init"}`** (`src/kb/templates.ts`) пишет три шаблона зарезервированных страниц: `project` (что за проект, стек, раскладка, команды сборки и проверок, соглашения, острые углы), `user-intent` (цель, приоритеты, ограничения, что вне scope, как работать с пользователем) и `onboarding` — вводный гайд для агента без контекста: порядок чтения от дешёвого к дорогому (`project_brief` → `project` → `user-intent` → `task_show` → `search`), что делать в процессе (патчить Σ после каждого значимого шага, записывать узнаванное сразу, одна содержательная строка в `summary`), и что сделать до остановки (реальные проверки в `verifications`, обновить `project`, `task_finish` или точный `next.action`).

Шаблоны пишутся со `status: 'stale'` и плейсхолдерами `<…>`, в теле каждой — приказ заполнить и поставить `current`, а отчёт `init` называет следующий вызов. `init` **никогда не перезаписывает** существующую страницу (отчёт разделяет `created` и `existing`): это первый вызов агента, который проекта не знает, а заполненное описание проекта — самое ценное в его базе; переписать страницу можно только явным `put`. Чтобы незаполненный шаблон не читался как документированная правда, в строке брифа у зарезервированных страниц теперь печатается статус: `- project (stale): TEMPLATE — fill in: …`.
