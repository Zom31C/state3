# План интеграции: SKILL.state в реальные кодинг-агенты

**Цель (подтверждена пользователем 05.09.2026):** довести инструмент до практической пользы — основной класс задач **разработка ПО**, форма применения **интеграция в существующие ИИ-агенты** (Qwen Code, opencode и т.п.), безопасность — **подтверждение опасных действий**.

**Идея:** кодинг-агенты на длинных задачах (рефакторинги, миграции, многофайловые фичи) раздувают транскрипт и теряют прогресс после сжатия/обрыва. Мы даём агенту внешний детерминированный слой состояния Σ из статьи: агент патчит состояние через инструменты, сервер валидирует патчи (модель не может испортить состояние), а компактная Σ инжектируется в контекст и переживает сжатие сессии.

Базовый проект (Фазы 0–4, воспроизведение arXiv:2608.26263) завершён — см. PLAN.md. Этот план — Фазы 5–9.

## 1. Архитектура (три слоя)

```
┌─────────────────────────────────────────────────────────┐
│ Адаптеры агентов                                         │
│  Qwen Code: extension (MCP + UserPromptSubmit hook       │
│             + skill /long-task)                          │
│  opencode:  mcp-конфиг + plugin (compacting hook)        │
│             + AGENTS.md                                  │
├─────────────────────────────────────────────────────────┤
│ MCP-сервер state3 (переносимое ядро интеграции)      │
│  tools: task_start / task_show / task_patch /            │
│         task_finish / task_list / task_history           │
│         page / search / project_brief                    │
├─────────────────────────────────────────────────────────┤
│ Ядро состояния и базы знаний (Фазы 0–4 + раздел 12)      │
│  DevTaskState zod-схема, mergeState ⊕, guard,            │
│  персистенция .state3/state.db (SQLite + FTS5)       │
└─────────────────────────────────────────────────────────┘
```

Принцип: **MCP-сервер — единая точка интеграции** для любого MCP-совместимого агента; адаптеры добавляют лишь (а) инжекцию Σ в контекст и (б) инструкцию P. Сам state3 **не исполняет побочных действий** (только读写 файлов состояния) — опасные операции исполняет хост-агент через свою систему разрешений.

## 2. Схема состояния дев-задачи (DevTaskState)

Статическая схема на домен «задача разработки» (по статье: одна схема на домен, не на задачу). С 09.09.2026 это **один навык из нескольких**: схема, guard и процедура P упакованы в `devTaskSkill()` (`src/tasks/schema.ts`) и зарегистрированы в реестре навыков (`src/tasks/registry.ts`) рядом с `supervise-task` — обобщение описано в разделе 11.

```jsonc
{
  "goal": "string — задача, одна-две фразы",
  "status": "active | blocked | done",
  "plan": [{ "id": "1", "task": "…", "status": "pending|in_progress|done|skipped", "notes": "…" }],
  "artifacts": { "<путь/файл>": "что изменено, текущий статус" },
  "verifications": [{ "check": "npm test", "status": "pass|fail|pending" }],
  "decisions": ["решение + причина — только то, что нужно будущим шагам"],
  "blockers": ["…"],
  "next": { "action": "конкретный следующий шаг", "risk": "safe|destructive|external" },
}
```

Правила ведения (часть P): хранить только нужное будущим шагам; завершённое сжимать до результата; `null` удаляет ключ; после каждого значимого шага — `task_patch`.

Guard домена (детерминированный): плановый элемент нельзя вернуть из `done` в `pending` без явной пометки в notes (аналог «преждевременной перезаписи» из статьи); `status: done` задачи нельзя снять без архивации.

## 3. MCP-сервер (Фаза 6)

- Стек: `@modelcontextprotocol/sdk` (TypeScript, stdio-транспорт), запуск `node dist/mcp/server.js` (или `npx tsx src/mcp/server.ts` в dev).
- Каталог состояния: `.state3/` в корне проекта (git-игнорируется по желанию), в нём один файл `state.db` (SQLite, WAL): задачи, история патчей (аудит), страницы базы знаний и связи между ними. Атомарность — транзакцией; легаси-корень из `<id>.json`/`<id>.history.jsonl` переносится подкомандой `task migrate` (раздел 12).
- Инструменты:
  | Tool            | Аргументы                     | Поведение                                                                                                                               |
  | --------------- | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
  | `task_start`    | `goal`, `plan?`               | создаёт задачу, возвращает компактную Σ + краткую P-инструкцию                                                                          |
  | `task_show`     | `id?` (по умолчанию активная) | компактная Σ (JSON без пробелов) + P-напоминание                                                                                        |
  | `task_patch`    | `patch`                       | валидация (zod + guard) → mergeState ⊕ → атомарная запись; при ошибке — диагностическое сообщение (агент ретраит, состояние не тронуто) |
  | `task_finish`   | `summary`                     | status=done, архивирует                                                                                                                 |
  | `task_list`     | —                             | все задачи проекта со статусами                                                                                                         |
  | `task_history`  | `id`, `limit?`                | последние патчи (аудит/откат вручную)                                                                                                   |
  | `project_brief` | —                             | карта базы знаний: по строке на страницу, в бюджете 4000 символов и без тел (§12.7)                                                     |
  | `page`          | `op` и аргументы операции     | база знаний: `get`/`put`/`list`/`delete`/`init`/`link`/`unlink`/`links` (§12.4–12.5)                                                    |
  | `search`        | `query`, `kind?`, `limit?`    | полнотекстовый поиск по задачам и страницам, совпадения со сниппетами (§12.6)                                                           |
- Активная задача одна на проект (последняя `active`); `task_show`/`task_patch` без id работают с ней.
- Дополнение от 09.09.2026 (раздел 11): у всех шести инструментов появился необязательный аргумент `project` (имя объявленного корня состояния), у `task_start` — ещё `skill` и `notation`, а `task_list` дописывает строки возможностей `skills: …` и `projects: …`.
- Дополнение от 12.09.2026 (раздел 12): инструментов **девять** — к шести `task_*` добавились `project_brief`, `page` и `search`. Все три принимают тот же аргумент `project`, поэтому супервизор читает базу знаний рабочего проекта так же, как его Σ.

## 4. Адаптер Qwen Code (Фаза 7)

Упаковка — **Qwen Code extension** (bundled-механизм: расширения поддерживают QWEN.md-контекст, commands, skills, agents, MCP-серверы, settings, hooks):

1. **MCP-сервер** из Фазы 6 в манифесте расширения.
2. **UserPromptSubmit hook**: если есть активная задача — добавляет в контекст каждого хода блок `## Active task state (state3)` с компактной Σ (аналог промпта A.4: модель видит состояние, а не транскрипт). На `SessionStart` к нему добавляется блок `## Project brief (state3)` — карта базы знаний проекта (§12.7): старт сессии — единственный момент, когда транскрипт ещё пуст и ориентироваться не по чему.
3. **Skill `/long-task`**: инструкция P — когда начинать задачу, как вести Σ, что после каждого значимого шага нужен `task_patch`, что `next.risk: destructive|external` требует подтверждения пользователя до исполнения.
4. Локальная установка/проверка — через механизм link/test расширений (см. bundled skill `extension-creator`).

## 5. Адаптер opencode (Фаза 8)

Проверено по docs (05.09.2026):

- **MCP**: `opencode.json`/`opencode.jsonc` (проект или глобально), верхний ключ `mcp`:
  ```jsonc
  {
    "$schema": "https://opencode.ai/config.json",
    "mcp": {
      "state3": {
        "type": "local",
        "command": ["node", "<путь>/dist/mcp/server.js"],
        "enabled": true,
      },
    },
  }
  ```
- **Plugin**: JS/TS-модуль в `.opencode/plugins/` (проект) или `~/.config/opencode/plugins/` (глобально); типизация `@opencode-ai/plugin@1.18.26` — именованный экспорт асинхронной функции `(input: PluginInput) => Promise<Hooks>`, где `input = {client, project, directory, worktree, experimental_workspace, serverUrl, $}`. Реализованные хуки:
  - `experimental.session.compacting(input, output)` — **инжекция Σ в контекст сжатия**: `output.context.push(...)` с текущим состоянием задачи → прогресс переживает compaction (документированный паттерн «Include any state that should persist across compaction»).
  - `experimental.chat.system.transform(input, output)` — `output.system.push(Σ)`: компактная Σ в системном промпте каждого запроса. Присутствует в типах 1.18.26, в публичной документации не описан; проверен живым прогоном — модель цитирует `goal` из Σ без единого вызова инструмента.
  - `tool.execute.before` — opt-in guard (`STATE3_GUARD=1`): `throw` отменяет вызов `bash`/`write`/`edit`/`patch`, если `next.risk` активной задачи `destructive` или `external`.
- **AGENTS.md**: блок P-инструкций (тот же текст, что skill `/long-task`); инструменты MCP видны агенту как `state3_task_*`.
- **Каталог проекта**: opencode передаёт `worktree: "/"`, когда проект не является git-репозиторием (`project.id === "global"`), а Bun считает `"/"` абсолютным путём. Плагин отбрасывает корни ФС, предпочитает `directory` и выбирает тот каталог, где уже лежит `.state3/`.

## 6. Безопасность (подтверждение опасных действий)

1. state3 сам не исполняет shell/HTTP/правки — только файлы `.state3/` (невредимо).
2. `next.risk: safe|destructive|external` в Σ; инструкция P **требует** запросить подтверждение пользователя перед исполнением destructive/external.
3. Хост-агент обеспечивает второй уровень: approval-режимы Qwen Code, permission-система opencode (`permission.asked/replied`).
4. Опционально (Фаза 8): opencode-plugin `tool.execute.before` блокирует bash/write, если активная задача имеет неподтверждённый destructive-next.

## 8. Критерии успеха

1. В Qwen Code и opencode агент ведёт дев-задачу через `task_*`; состояние хранится в `.state3/`, патчи валидируются сервером.
2. После сжатия сессии (`/compact` в Qwen Code, compaction в opencode) или перезапуска агент **восстанавливает прогресс из Σ без потерь** — главный практический выигрыш.
3. Невалидный патч никогда не портит файл состояния; история патчей аудиторна.
4. Опасные действия помечены `next.risk` и исполняются только после подтверждения (инструкция P + permission-система хоста).
5. Все проверки проекта зелёные (typecheck/lint/тесты), новые модули покрыты тестами.

## 9. Проверенные факты об интеграционных поверхностях (05.09.2026)

- **Qwen Code** (проверено 05.09.2026 по живой установке **0.22.3** — `qwen --version`: `lib/bundled/extension-creator/SKILL.md`, `lib/bundled/qc-helper/docs/**`, `lib/examples/{mcp-server,starter,skills}/`, `lib/chunks/*`; в кэше обновлений лежит также копия 0.21.6, и более ранние пометки «0.21.6» в этом документе относились к ней):
  - манифест — `qwen-extension.json` в корне расширения (без точки в начале); поля: `name`, `version`, `displayName`, `description`, `contextFileName` (по умолчанию `QWEN.md`), `mcpServers`, `settings` (запросы env-переменных), `hooks`, `channels`, `lspServers`;
  - path-переменные `${extensionPath}`, `${workspacePath}`, `${/}` гидратируются в полях `command`, `args`, `cwd`, `env`, `headers`, `url`, `trust` у `mcpServers` и в `command` inline-хуков; в file-based `hooks/hooks.json` подставляется только `${CLAUDE_PLUGIN_ROOT}`. **`${workspacePath}` — это каталог запуска `qwen`** (`targetDir`/`workingDirectory`), а не каталог проекта, подключённого к сессии; `${workspaceFolder}` не поддерживается и раскрывается в пустую строку (проверено: сервер с таким `cwd` не стартует — `Disconnected`);
  - окружение дочернего процесса MCP-сервера = окружение хоста плюс `env` из манифеста. Хост передаёт `QWEN_CODE=1`, `QWEN_CODE_SESSION_ID`, `QWEN_CODE_MODEL`, `QWEN_CODE_PROJECT_DIR` и др.; **`QWEN_CODE_PROJECT_DIR` — это служебный каталог данных `~/.qwen/projects/<slug от каталога запуска>`**, а не каталог исходников проекта, поэтому как корень состояния непригоден (измерено временным зондом);
  - хуки: тип `command` получает JSON в stdin — документированные общие поля `session_id`, `transcript_path`, `cwd`, `hook_event_name`, `timestamp` плюс поля события (у сабагентов также `agent_id`/`agent_type`); **семантика `cwd` в документации не определена** (каталог запуска или каталог сессии). Хук возвращает JSON в stdout (`hookSpecificOutput.additionalContext`); exit 0 — успех, exit 2 — блокирующая ошибка (stderr уходит модели), прочие коды — неблокирующие; `timeout` в **миллисекундах**; у `UserPromptSubmit` нет `matcher`, у `SessionStart` matcher — по источнику (`startup|resume|clear|compact`), есть также `PreCompact`/`PostCompact`;
  - инжектированный контекст попадает в ход обёрнутым в `<qwen:user-prompt-submit-context>`;
  - ресурсы: `skills/<name>/SKILL.md` (frontmatter `name`, `description`, `argument-hint`), `commands/<name>.md` (подкаталог → `/ns:name`), `agents/<name>.md`, `QWEN.md`;
  - установка: `qwen extensions new|link|install|list|uninstall|settings`; `link` создаёт symlink (правки подхватываются), после подключения нужен перезапуск сессии;
  - **`/cd` и `/reload-plugins` не пересоздают дочерний процесс MCP-сервера расширения** (измерено 09.09.2026): `/cd <dir>` меняет каталог сессии — inline-хуки сразу начинают читать Σ нового каталога, — но сервер остаётся с тем `cwd`, который получил при старте; `/reload-plugins` («Reload extension changes (commands, skills, agents, hooks, MCP/LSP servers) from disk») процесс тоже не перезапускает: pid и время его старта не изменились ни после `/cd`, ни после `/reload-plugins`. Единственное исправление — запуск `qwen` из каталога проекта либо `STATE3_STATE_DIR`;
  - **живой сервер расширения держит в памяти старый скомпилированный код** (измерено 09.09.2026): после `npm run build` уже запущенная сессия Qwen Code продолжала отвергать path-ключи (`{"plan[1].status":"done"}`) как `unknown-key`, тогда как CLI проекта с тем же `dist` их принимал. Причина та же, что и у пункта выше: лаунчер расширения один раз делает `import` `dist/mcp/server.js` при старте дочернего процесса, и ни `/cd`, ни `/reload-plugins` процесс не пересоздают. Помогает только перезапуск `qwen`;
  - проверка: `qwen mcp list` (статус `Connected`), диалог `/mcp`, `qwen --debug` (лог `[TRUSTED_HOOKS]`, `[SKILL_LOAD]`, `[MCP]`), `QWEN_DEBUG_LOG_FILE`;
  - `~/.qwen/tmp/<hash>/logs.json` — **персистентная история пользовательских промптов** (не лог одной сессии): по ней можно восстановить, какие команды (`/cd`, `/compact`, `/reload-plugins`) и когда выполнял пользователь, в том числе в прошлых сессиях;
  - MCP-инструменты в сессии видны как `mcp__<server>__<tool>`.
- **opencode** (1.18.26): MCP — ключ `mcp` в `opencode.json(c)`, `type: "local"`, `command: [...]`, опции `cwd/environment/enabled/timeout` (docs/mcp-servers). Плагины — `.opencode/plugins/` или `~/.config/opencode/plugins/`, `PluginInput = {client, project, directory, worktree, experimental_workspace, serverUrl, $}`; хуки: `experimental.session.compacting` (инжекция в промпт сжатия), `experimental.chat.system.transform` (`output.system.push` — инжекция в системный промпт каждого запроса; присутствует в типах, но не в публичной документации), `tool.execute.before/after` (`throw` отменяет вызов), `session.*`, `message.*`, `permission.*`, `todo.updated`, `tui.prompt.append` и др. Проект без git-репозитория даёт `project.id === "global"` и `worktree: "/"`.
- **Локальная модель как провайдер Qwen Code** (измерено 09.09.2026, RTX 3090 24 GiB VRAM / 16 GiB RAM, i7-10700K): LM Studio на `127.0.0.1:1234/v1`, модель `qwen/qwen3.8-27b` Q4_K_M (веса 16.52 GiB, GGUF допускает ctx до 262144). Загрузка при ctx 65536 / 73728 / 81920 / 131072 занимает практически одинаковые ~24.2 GiB VRAM (загрузчик насыщает видеопамять независимо от длины контекста), зато растёт расход системной RAM: свободная падает с 1.4 GiB до 0.42 GiB — KV-кэш частично уходит туда. `lms load --estimate-only` для оценки непригоден: не учитывает KV-кэш (одинаковые 16.52 GiB при любом ctx, `Confidence: LOW`). Итог: ctx **81920** — и в LM Studio (`lms load qwen/qwen3.8-27b -c 81920 -y`), и в `generationConfig.contextWindowSize` провайдера в `~/.qwen/settings.json`. Значения обязаны совпадать: если лимит хоста больше загруженного контекста, длинные запросы упираются в реальное `loaded_context_length` (видно в `GET /api/v0/models`). Перезагрузка модели через CLI не сохраняется как конфигурация по умолчанию — после перезагрузки LM Studio контекст нужно задать снова (либо в UI, либо тем же `lms load`).
- **Общее**: оба агента — MCP-хосты ⇒ ядро интеграции (MCP-сервер) пишется один раз.

## 11. Обобщение рантайма: навыки, проекты, нотация, path-патчи (09.09.2026)

Фазы 5–9 строили ядро вокруг одного домена. Четыре обобщения ниже делают рантайм, инструменты и хранилище доменно-нейтральными: новый домен приносит свой навык, а не правку ядра. Все четыре реализованы и покрыты тестами.

### 11.1 Реестр навыков

Навык — это Σ-схема + доменный guard + текст процедуры P + `initialState`. Интерфейс `Skill` (`src/core/skill.ts`):

| Поле                        | Назначение                                                         |
| --------------------------- | ------------------------------------------------------------------ |
| `name`                      | имя навыка; попадает в запись на диске и в вывод инструментов      |
| `schema`                    | схема Σ (strict: неизвестные ключи отклоняются)                    |
| `guard?`                    | доменные правила; проверяются до схемы                             |
| `instructions`              | процедура P этого навыка                                           |
| `initialState`              | Σ₀ — обязана проходить схему                                       |
| `newPlanItem?(task, index)` | как строка шага становится элементом плана: форму определяет домен |
| `progress?(state)`          | счётчики `done`/`total` для списков; без него — 0/0                |

Реестр — `src/tasks/registry.ts`: `createSkillRegistry(skills, defaultName)`, `builtinSkills()`, `builtinSkillRegistry()`, `DEFAULT_SKILL_NAME = 'dev-task'`. Встроенных навыков два: `dev-task` (`src/tasks/schema.ts`) и `supervise-task` (`src/tasks/supervise.ts`).

Запись задачи (тогда — файл `.state3/<id>.json`, с 12.09.2026 — строка таблицы `task` в `.state3/state.db`, раздел 12) несёт поля `skill` и `notation`:

- запись без них (написанную прежним рантаймом) читают как `dev-task` / `plain` и нормализуют при следующей записи — проверено на реальной записи от 07.09.2026;
- запись с именем навыка, которого у рантайма нет: `show`/`patch` бросают ошибку категории `skill` с перечислением доступных навыков, а `list` пропускает её молча — чужая или повреждённая запись не должна ломать список.

`TaskStore.finish()` один на все навыки, потому что любая Σ несёт одинаковый контракт завершения: `status`, append-only массив `decisions` и `next {action, risk}`.

Тексты процедур собираются из общих блоков `src/tasks/procedure.ts` (`RISK_RULES`, `PATCH_SEMANTICS`, `STATE_HYGIENE`, `composeProcedure`), поэтому семантика слияния и таксономия рисков имеют один источник истины для обоих навыков.

### 11.2 Корни состояния нескольких проектов

Все шесть MCP-инструментов принимают необязательный аргумент `project`; CLI — флаг `--project <name>` (вместо `--root`, который с ним несовместим).

Корни **объявляются заранее, и достижимы только объявленные**:

- сервер: `--project name=dir` (повторяемый) — `src/mcp/server.ts`;
- окружение: `STATE3_PROJECTS` = `name=dir;name2=dir2` (разделитель `;` или перевод строки) либо JSON-объект `{"name":"dir"}` — `parseProjectsSpec` (`src/tasks/projects.ts`);
- имя проекта обязано соответствовать `/^[a-z0-9][a-z0-9_-]{0,63}$/`; относительный каталог разрешается против cwd; повтор имени — ошибка.

Это и есть аргумент безопасности: объявление приходит из окружения пользователя или конфигурации хоста и никогда от модели, а модель выбирает только **имя** из объявленного списка. Направить инструменты в произвольный каталог — прочитать его или записать в него — она не может.

Неизвестное имя даёт ошибку с перечислением объявленных корней. Проверено: `unknown project "nope" — declared: racegame (D:\Projects\RaceGame\.state3)`.

`task_list` дописывает строки возможностей `skills: …` и `projects: …`, чтобы модель узнавала, что существует, без отдельного инструмента.

Хук Qwen Code (`extensions/state3/hooks/inject-state.mjs`) при заданной `STATE3_PROJECTS` инжектирует также активную задачу каждого объявленного проекта — блоком `## Supervised projects (state3)` с подзаголовком `### <name> — <rootDir>` и теми же строками Σ, что и для основной задачи (заголовок с навыком, однострочная Σ, напоминание компактной нотации, подсказка о размере). Подробности поведения, считанные из файла хука:

- корень, совпадающий с основным, пропускается (на Windows сравнение без учёта регистра), чтобы Σ не инжектировалась дважды;
- нечитаемый корень и проект без активной задачи пропускаются, не скрывая остальные;
- некорректное объявление (`STATE3_PROJECTS` не разбирается) отключает всю секцию: хук не имеет права ронять ход;
- секция заканчивается подсказкой `Patch these with the project argument: task_patch {"project":"<name>", …}.`

Целевой сценарий: одна супервизирующая сессия читает и патчит состояние рабочего агента, запущенного в другом каталоге проекта.

### 11.3 Компактная нотация и дешёвые path-патчи

**Нотация** (`src/tasks/notation.ts`) — свойство задачи: `plain` (по умолчанию) или `compact`. Для `compact` к процедуре P добавляется блок с требованием писать значения Σ как сжатый псевдокод: без артиклей и вводных слов, символы `->` `+` `-` `=` `!` `?`, одна запись — одна строка, пути, идентификаторы, команды, тексты ошибок и числа дословно, и никогда не сжимать ограничение, причину или падающую команду. Основание: Σ реинжектируется каждый ход, поэтому её размер — повторяющаяся стоимость; сильнее всего это важно для локальных моделей с небольшим контекстом (замер потолка — раздел 9). `renderTaskHead` печатает для compact-задачи однострочное напоминание, поэтому хосты, инжектирующие Σ без P (хуки, адаптеры), тоже его получают.

**Path-ключи патча** адресуют один элемент массива:

```json
{
  "plan[1].status": "done",
  "rounds[0].verdict": "accepted",
  "decisions[+]": "…",
  "plan[+]": { "id": "3", "task": "…" }
}
```

Индексы с нуля, `[+]` — добавление в конец. Ниже элемента можно адресовать и вложенные ключи: недостающие объекты создаются (`assignAtTail`), что покрыто тестами ядра, хотя у обоих встроенных навыков элементы массивов плоские. Реализация — `expandPathPatch(state, patch)` в `src/core/state.ts`: она переписывает path-ключи в обычный патч «массив целиком» **до** guard'а и валидации схемы, поэтому path-ключ не может обойти доменное правило. Тест это фиксирует (`tests/tasks/store.test.ts`): переоткрытие `done`-пункта плана path-ключом отклоняется guard'ом, а тот же патч вместе с непустым `plan[0].notes` проходит.

Адресуемы только массивы: обычные объекты и так сливаются рекурсивно, а точечные ключи над ними неоднозначны, потому что ключи `artifacts` — это пути файлов (`artifacts.INTEGRATION.md`).

Ограничения, у каждого своё сообщение и категория `path`: индекс вне диапазона (сообщение указывает на `field[+]`), путь в поле-не-массив, `null` на элемент или на `[+]` (удаление path-ключом невыразимо — пришлите массив без этого элемента), ключи ниже `[+]`, путь в элемент-не-объект, и одно поле одновременно целиком и path-ключом в одном патче.

История пишет патч **как он был отправлен** (с path-ключами), а не его раскрытие: аудит показывает, что запросил агент и во сколько символов это обошлось.

### 11.4 Второй встроенный навык: `supervise-task`

Σ (`src/tasks/supervise.ts`): `{ goal, status, spec, worker, rounds: [{ id, assignment, verdict, evidence, feedback }], decisions, blockers, next }`, где `verdict` — `pending` | `accepted` | `rejected`. Прогресс в списках — принятые раунды ко всем. Навык объявлен без `newPlanItem`, поэтому `task_start` с планом для него отклоняется: `skill "supervise-task" takes no plan; start it with a goal, then patch the fields task_show lists`.

Guard: завершённую задачу нельзя переоткрыть; `blocked` требует хотя бы один блокер; `accepted` требует непустого `evidence`; `rejected` требует непустого `feedback`; одновременно может быть не более одного `pending`-раунда.

P описывает цикл: одно задание → рабочий агент его исполняет → супервизор проверяет результат сам (читает файлы, запускает проверки, никогда не принимает на слово рабочего) → вердикт и `evidence`, при отказе — `feedback`, по которому рабочий исправит без догадок → следующее задание. Там же зафиксировано, что запуск рабочего внутри его собственного проекта — `safe`, а правка конфигурации пользователя, глобальная установка и любая публикация — `external`.

### 11.6 Словарь отказов: один источник на трёх потребителей (10.09.2026)

Категории отказа записи жили в четырёх копиях: тип `ValidationErrorCategory` в `src/core/validator.ts` (четыре значения), `TaskPatchError.category: string` в `src/tasks/store.ts` (который бросал ещё `path`, `skill` и `notation`), `switch` подсказок в `src/mcp/tools.ts` и список в тексте процедуры P. Попутно тест вскрыл тонкость zod: значение не из `enum` она относит к `invalid_value`, поэтому `type-coercion` достижим только на не-enum полях.

### 11.7 Заблокированная задача остаётся открытой (10.09.2026)

`status: "blocked"` делал задачу невидимой для всех инструментов, вызванных без `id`: `TaskStore.activeId()` искал ровно `status === 'active'`, поэтому `task_show`, `task_patch`, `task_finish` и `task_history` отвечали `No active task found`. Тот же фильтр был в хуке расширения (`pickActive` в `extensions/state3/hooks/inject-state.mjs`), из-за чего Σ заблокированной задачи не инжектировалась в контекст — то есть исчезала ровно в той сессии, которая должна её разблокировать после `/compact`. Дефект найден эмпирически: задача этой супервизии была переведена в `blocked` и потеряла доступ к собственному состоянию.

Исправление в обоих слоях одинаковое: открытой считается задача не в `done`, при этом `active` имеет приоритет над `blocked`, поэтому поведение сессии с одной активной задачей не меняется. `activeId()` возвращает самую свежую по `updatedAt` (список уже отсортирован), хук выбирает по тому же признаку. Проверено тестами (`tests/tasks/store.test.ts`: заблокированная задача находится и патчится без `id`, активная побеждает заблокированную) и прогоном хука на реальной `blocked`-задаче: Σ инжектируется с пометкой `(blocked)`.

Метрики: build/typecheck/lint/format:check зелёные, 551 тест / 27 файлов, прогон хука на `blocked`-задаче даёт `additionalContext` с её Σ.

### 11.9 `null`-удаление несуществующего ключа больше не проходит молча (11.09.2026)

Дефект найден эмпирически на собственной Σ: сжимая `artifacts`, супервизор отправил `{"artifacts.src/": null}`, полагая, что ключи объекта адресуются через точку так же, как элементы массива. `PATH_KEY` распознаёт только поля-массивы, поэтому ключ остался обычным полем верхнего уровня со значением `null`; `mergeState` выполняет `delete result[key]` **до** валидации, а удаление отсутствующего ключа — ничто. Строгая схема (`z.strictObject`) не увидела чужого поля, и патч ответил `Patched`, оставив в Σ ровно ту запись, которую агент считал удалённой. Это худший класс отказа: состояние расходится с убеждением агента, и расходится молча.

Исправление — `findMalformedDeleteKeys(patch)` в `src/core/state.ts`: синтаксический фильтр по ключам верхнего уровня (значение `null`, ключ не парсится как path-ключ и содержит `.` или `[`). `validatePatch` сообщает их до слияния как категорию `unknown-key`, называя ключ и две законные формы: path-ключ для поля-массива и вложенный словарь для ключей объекта. Дополнительно `assignAtTail` отклоняет `null` по leaf-ключу, которого у элемента массива нет (категория `path`), поэтому опечатка `plan[0].note` тоже не проходит незамеченной.

Граница правила выбрана намеренно: удаление **плоского** отсутствующего ключа остаётся законным. В навыке `warehouse` «пустая полка» означает «ключа нет в Σ» (поля схемы `.optional()`, SHIP/MAINTAIN удаляют ключ), поэтому `MAINTAIN` по уже пустой полке обязан принимать `{shelf_7: null}`. Первая версия проверки отвергала именно это и ломала `tests/matrix.test.ts` (`judged` = 3 вместо 4) — регрессия и задала окончательную формулировку. Проверить «известно ли схеме это поле» нельзя: `StateSchema` намеренно открывает только `safeParse`, ядро не знает про zod, поэтому проверка синтаксическая и от навыка ничего не требует.

Метрики: build/typecheck/lint/format:check зелёные, 583 теста / 29 файлов (+9: `findMalformedDeleteKeys` 5, `expandPathPatch` 1, `validatePatch` 2, `TaskStore.patch` 1); `matrix` снова зелёный.

## 12. Единая база состояния и база знаний проекта (11–12.09.2026)

Фазы 5–9 решали одну половину задачи: прогресс **текущей** задачи переживает сжатие сессии. Вторая половина — знания **проекта**: что это за проект, чего от него хочет пользователь, как в нём начинать работу, что делает каждая фича и почему решения приняты так, а не иначе. Без неё каждая новая сессия начинает с нуля и задаёт пользователю вопросы, на которые проект уже ответил, а ответы живут в транскрипте, который сжимается и теряется.

Обе половины легли в один файл — `.state3/state.db` (SQLite): задачи и страницы ищутся одним полнотекстовым индексом и связываются друг с другом рёбрами. Модель — «Jira + Confluence для LLM», с той разницей, что читатель один и платит токенами, поэтому у данных три уровня детализации (§12.5), а у «вводного гайда» — жёсткий бюджет (§12.7).

### 12.1 Один файл состояния вместо набора JSON

`.state3/state.db`: `better-sqlite3` 12.11.1 (prebuild под Node 20.18.1/win-x64; `node:sqlite` на этой версии недоступен), журнал WAL, версия схемы в таблице `meta` (`SCHEMA_VERSION = 1`). Таблицы: `task`, `task_history`, `page`, `link`, `search` (виртуальная FTS5-таблица, синхронизируемая триггерами с `page` и `task`).

Слой `src/db/`: `schema.ts` (DDL и версия), `database.ts` (порт `SqlDatabase`, `openStateDatabase(path, {readOnly|mustExist|noMkdir})`, `ensureSchema`, `checkpoint`). Порт нужен, чтобы сторы не знали про драйвер: тесты подменяют его, а рантайм открывает одно соединение на корень.

`TaskStore` переведён на базу без изменения публичного контракта — те же `start`/`show`/`patch`/`finish`/`list`/`history`, та же валидация патча до записи; изменился только `meta.path` (теперь это `state.db`) и способ хранения: запись задачи и её история пишутся одной транзакцией, соединение открывается лениво и закрывается владельцем (сервер закрывает все созданные сторы при выходе, поэтому WAL сворачивается и корень остаётся одним файлом).

### 12.2 Миграция легаси-корней и диагностика

- `npm run run -- task migrate` — переносит `<id>.json` и `<id>.history.jsonl` в `state.db`; легаси-файлы **архивируются**, а не удаляются (`--purge` — удалить вместо архива). Записи переносятся дословно: миграция не имеет права переинтерпретировать чужую Σ.
- `npm run run -- task doctor` — отчёт о корне: `PRAGMA integrity_check`, версия схемы, счётчики задач/истории/страниц/связей, нечитаемые строки и **висячие рёбра** (связь, у которой нет одного из концов, — см. §12.4).

Обе подкоманды работают с самим корнем, а не с активной задачей, поэтому `migrate` и `doctor` не требуют открывать стор задач обычным путём. Живой корень этого проекта мигрирован: 4 задачи и 79 записей истории на момент переноса; `doctor` после миграции — schema v1, integrity ok. Повторный `doctor` 12.09.2026: tasks 4, history 88 (аудит пополняется каждым патчем), pages 0, links 0, indexed 4.

### 12.3 Хук читает базу (дефект, найденный по ходу)

Хук `inject-state.mjs` — второй потребитель состояния, и он срабатывает на **каждом** промпте. После перевода стора на базу он продолжал читать JSON-файлы, то есть расширение молча теряло Σ в каждом мигрированном проекте: инструменты работали, а инжекции не было. В плане этого пункта не было — найден при обходе потребителей хранилища.

Исправление: компилируемая половина чтения вынесена в `src/tasks/inject.ts` (`readInjection(rootDir, options)`), хук находит её через `extensions/state3/lib/home.mjs` (общее для сервера и хука разрешение сборки: `STATE3_HOME` → обход каталогов вверх по маркерным файлам) и вызывает из `dist/tasks/inject.js`. Легаси-JSON остался фолбэком для корня без базы — немигрированный проект продолжает работать.

Два решения, принятых после замеров, а не по вкусу:

- ридер открывается `{mustExist: true}`, **не** `readOnly`: зонд показал, что read-only-соединение не удаляет `-wal`/`-shm` при закрытии, поэтому хук оставлял бы два лишних файла в корне на каждом промпте;
- корень со `state.db` **авторитетен**: лежащий рядом легаси-JSON не читается, потому что миграция его архивировала и фолбэк инжектировал бы устаревшую Σ. Нечитаемая база даёт строку в stderr и пустой stdout — ход не блокируется, но пропажа Σ больше не тихая.

Тот же обход потребителей нашёл вторую половину того же дефекта — и уже в адаптере, которого план не касался. Плагин opencode (`adapters/opencode/plugin/state3.js`) перебирал только `*.json` в корне состояния, поэтому в мигрированном проекте не находил ни одной записи: Σ молча исчезала из контекста, а opt-in guard (`STATE3_GUARD=1`) терял `next.risk` и переставал блокировать опасные вызовы — то есть ломалась не только инжекция, но и слой безопасности. Подтверждено 12.09.2026 на живом корне: `--self-test` плагина отвечал `no active task in D:\Projects\skillState\.state3`, тогда как хук Qwen Code на том же каталоге печатал Σ активной задачи.

Закрыто тем же днём по тому же образцу: плагин находит сборку (`STATE3_HOME` → обход каталогов вверх от своего файла, маркер `dist/tasks/inject.js`) и зовёт `readInjection`, а легаси-JSON остаётся путём для корня без базы. Ради guard'а `readInjection` возвращает теперь и `next.risk` задачи, пропущенный через словарь `RISK_LEVELS`: уровень риска обязан приходить из того же чтения, что и текст, иначе два запроса к одной базе могут разойтись, и host будет блокировать вызовы не по тому состоянию, которое показал модели. Цена — автономность файла стала частичной: копия в `.opencode/plugins/` без `STATE3_HOME` сборку не найдёт и напишет в лог `warn` вместо Σ (молча ничего не пропадает). Бриф плагин вводит на первом запросе сессии и при сжатии: события «старт сессии» у opencode нет, поэтому ключ — `sessionID` из аргумента хука, а без него — один раз на процесс. Проверка в `smoke:mcp` (плагин запускается на настоящей базе и печатает Σ вместе с брифом) и на живом корне: self-test снова печатает Σ.

### 12.4 База знаний: страницы и связи

Страница (`src/kb/schema.ts`): `id` (`/^[a-z0-9][a-z0-9_-]{0,63}$/`), `kind`, `title` (≤200), `summary` (≤200), `body` (≤20000), `parent`, `status` (`current|stale|archived`), `pin`, `createdAt`/`updatedAt`. Видов шесть: три **синглтона** — `project` (что за проект, стек, команды), `user-intent` (чего хочет пользователь, что вне scope), `onboarding` (как начинать работу) — их `id` равен виду, и повторяемые `feature`, `decision`, `note`.

`pageGuard` отклоняет до записи: синглтон под чужим id, несуществующего родителя, цикл в `parent` и глубину вложенности больше `PARENT_DEPTH_LIMIT` (100). Отказ несёт категорию из общего словаря (§11.6), поэтому `KbError` и `TaskPatchError` говорят с агентом на одном языке.

`PageStore.put` — create-or-update: пропущенное поле сохраняет прежнее значение, `parent: null` сбрасывает родителя. `delete` в той же транзакции убирает рёбра страницы, а её дети становятся корневыми (ответ перечисляет их: молчаливое переподвешивание — способ потерять дерево).

Связи (`src/kb/links.ts`) полиморфны: концы задаются как `page:<id>` или `task:<id>`, поэтому задача и страница связываются одним ребром с именем `rel` (`documents`, `implements`, `decides`, …). Внешний ключ на такой конец не поставить — значит висячее ребро возможно, и его считает поломкой `doctor`; создаётся ребро только между существующими объектами одного корня. Смысл связей для агента: от страницы фичи видно задачу, которая её сделала, а от задачи — что о ней написано.

### 12.5 Три инструмента вместо тридцати: `page`, `search`, `project_brief`

Инструментов по-прежнему **девять**: шесть `task_*` плюс три новых. Декларации инструментов стоят токенов в каждой сессии, поэтому `page` — один инструмент с аргументом `op` (`get`, `put`, `list`, `delete`, `init`, `link`, `unlink`, `links`), а не восемь отдельных; аргументы, которых операция не принимает, отклоняются (`op "get" does not take "summary"`), а не игнорируются.

Уровни детализации — ответ на «сколько стоит ориентирование»:

| Уровень | Что отдаёт                                     | Цена                            |
| ------- | ---------------------------------------------- | ------------------------------- |
| L0      | `project_brief` — по строке на страницу        | ≤4000 символов, тел нет вовсе   |
| L1      | `page get` / `task_show` — объект целиком      | одна страница или одна Σ        |
| L2      | `search` — совпадения со сниппетами ≈120 симв. | ≤50 совпадений, по умолчанию 10 |

Порядок чтения для агента без контекста: L0 → `search` → L1. Он же записан в шаблоне `onboarding` (§12.7).

### 12.6 Поиск: FTS5 с LIKE-фолбэком

`search` (`src/kb/search.ts`) ищет по задачам и страницам одним запросом: FTS5 `unicode61` по `title`/`summary`/`body` с весами bm25 10/5/1 (заголовок важнее тела), аргумент `kind` сужает до задач или страниц.

Запрос приходит от модели, поэтому он не должен уметь сломать MATCH: каждое слово кавычится в фразу и слова соединяются implicit AND — синтаксис FTS5 (`OR`, `*`, `NEAR`, `column:`) из запроса недостижим. При нуле совпадений или ошибке MATCH выполняется LIKE-скан подстроки: частичное слово и опечатка дают ответ, а не пустоту.

### 12.7 Холодный старт: бриф, шаблоны, вводный гайд

**Бриф** (`src/kb/brief.ts`) — L0 в жёстком бюджете 4000 символов. Режется целыми строками сверху вниз по приоритету (синглтоны → `pin` → `feature`/`decision`/`note`, внутри группы свежие выше) и никогда не пополам: обрезанное сообщается строкой `N more page(s)` и подсказкой `page list`, `archived` исключены, но их счётчик виден. Тест фиксирует главное свойство: бриф одинаков при пустом теле и при теле в 20000 символов — то есть стоимость ориентирования не зависит от того, насколько проект документирован.

**Хук вводит тот же бриф** секцией `## Project brief (state3)` после Σ — и **только на `SessionStart`, только для основного корня**. На промпте сессия бриф уже видела, и повтор стал бы налогом на каждый ход; у супервайзера он умножался бы на число объявленных проектов, которым достаточно `project_brief {"project":"<name>"}`. Пустая база не брифуется вовсе (`renderDatabaseBrief` возвращает `null`): иначе «страниц ещё нет» печаталось бы на старте каждой сессии каждого такого проекта, тогда как инструмент в том же случае отвечает развёрнуто и предлагает `init`.

**`page {"op":"init"}`** (`src/kb/templates.ts`) пишет три шаблона зарезервированных страниц: `project` (что за проект, стек, раскладка, команды сборки и проверок, соглашения, острые углы), `user-intent` (цель, приоритеты, ограничения, что вне scope, как работать с пользователем) и `onboarding` — вводный гайд для агента без контекста: порядок чтения от дешёвого к дорогому (`project_brief` → `project` → `user-intent` → `task_show` → `search`), что делать в процессе (патчить Σ после каждого значимого шага, записывать узнаванное сразу, одна содержательная строка в `summary`), и что сделать до остановки (реальные проверки в `verifications`, обновить `project`, `task_finish` или точный `next.action`).

Шаблоны пишутся со `status: 'stale'` и плейсхолдерами `<…>`, в теле каждой — приказ заполнить и поставить `current`, а отчёт `init` называет следующий вызов. `init` **никогда не перезаписывает** существующую страницу (отчёт разделяет `created` и `existing`): это первый вызов агента, который проекта не знает, а заполненное описание проекта — самое ценное в его базе; переписать страницу можно только явным `put`. Чтобы незаполненный шаблон не читался как документированная правда, в строке брифа у зарезервированных страниц теперь печатается статус: `- project (stale): TEMPLATE — fill in: …`.

### 12.9 Переносимый шаблон AGENTS.md (12.09.2026)

Правила для агента жили в двух копиях и только для двух хостов: `extensions/state3/QWEN.md` (англ., инжектируется расширением Qwen Code) и `adapters/opencode/AGENTS.md` (русск., копируется в корень проекта). Копии уже расходились — языком и составом, — а третьего случая, «проект на хосте, который просто читает `AGENTS.md`», не было вовсе: новый проект получал базу знаний и девять инструментов, но не получал ответа на вопрос «в каком порядке этим пользоваться».

Решение: один текст правил — `templates/AGENTS.md` (англ.), копируется в корень нового проекта; адаптер opencode сокращён до **дополнения**, где осталось только то, что у него устроено иначе (префиксы инструментов `state3_*`, инжекция плагином в системный промпт и в контекст сжатия, `STATE3_HOME` для корня с `state.db`, opt-in guard, один корень без `STATE3_PROJECTS`). Шаг 4 установки в README адаптера копирует шаблон и дописывает к нему дополнение. Язык шаблона — английский по выбору пользователя: файл попадает в проекты, которые может читать любой хост, а русская проза остаётся в документации репозитория.

Границу между шаблоном и процедурой провели по признаку «кто владеет текстом». Шаблон описывает **привычки** — когда читать, когда патчить, что документировать, когда спрашивать — и намеренно не копирует P: процедуру возвращает `task_show` вместе с Σ, из того же источника, что схема навыка и словарь отказов. Правила, продублированные в файле репозитория, устаревают молча, а P приходит из рантайма, который их и проверяет.

Отдельный раздел шаблона — «починить баг без контекста»: `project_brief` → `search` (текст ошибки дословно, затем файл/фича) → `task_history` родственной задачи (отклонённые патчи — это запись того, что уже пробовали) → `git log`/`git blame` → только потом код, и только тот, на который указали предыдущие шаги. Корень причины при этом записывается страницей `note` или `decision`: исправление принадлежит коду, а причина, по которой оно понадобилось, — базе знаний. До шаблона этот сценарий — главный, ради которого база знаний существует, — не был записан нигде как порядок шагов.

Последняя секция `## This project` — единственная, которую проект заполняет сам: команда проверки, файлы, которые нельзя трогать, соглашения, которые нельзя угадать, язык ответа. Плейсхолдеры `<…>` и требование держать секцию короче десяти строк: файл читается каждой сессией, поэтому всё длинное относится на страницу `project`, а не в `AGENTS.md`.

Проверка: `npm run lint && npm run typecheck && npm test && npm run format:check` (prettier форматирует `.md`, поэтому шаблон и правки README/INTEGRATION прогнаны через `prettier --write` по изменённым файлам). Поддержку `AGENTS.md` хостом не предполагали, а сверили с установленным Qwen Code: `AGENT_CONTEXT_FILENAME = "AGENTS.md"` в рантайме и `docs/features/memory.md` («If your repository already has an `AGENTS.md` file for other AI tools, Qwen reads that too»).

## 13. Делегирование сабагентам: ориентация вместо Σ (12.09.2026)

Разделы 5–12 закрывали одну сессию. Хосты умеют больше: Qwen Code делегирует работу сабагентам — отдельным контекстам, которые выбрасываются по завершении. Для state3 это одновременно союзник и дыра. Союзник — потому что сабагент уносит из контекста оркестратора простыни чтения и возвращает несколько строк. Дыра — потому что Σ в сабагент не попадала вовсе: хук висит на `UserPromptSubmit`, а старт сабагента не пользовательский промпт. Делегированный агент не знал ни что задача уже есть (и заводил вторую), ни какой шаг в работе (и переделывал закрытый).

### 13.1 Что инжектируется

`SubagentStart` (контракт хоста: `hookSpecificOutput.additionalContext` — «initial context for the subagent») получает **ориентацию**, а не Σ:

```
Task <id> [<skill>] (<status>)
goal: <goal>
in flight: <пункт плана со статусом in_progress — вместе с notes>
next: <next.action> [risk: <next.risk>]
blocked: <blockers через "; ">
```

Рендерит `renderTaskBrief` в `src/tasks/render.ts`; `readInjection(root, {subagent: true})` выбирает его вместо `renderTaskHead`. Легаси-корень без базы читает зеркало той же функции в хуке (`subagentBriefLines`) — по правилу, которое уже принято в §12.3: standalone-половина дублирует форму записи, чтобы расширение работало без сборки.

Расчёт: сабагент носит свой промпт на **каждом собственном ходе**. Σ в 4000 символов, умноженная на 12–40 ходов дешёвой модели, — расход, которого у оркестратора нет. Ориентация — десятки токенов, и её хватает на две конкретные ошибки, которые она предотвращает: вторая задача и переделанный шаг.

Поля взяты только те, что есть у обоих навыков рантайма: `goal`, `status`, `blockers`, `next{action,risk}`. Строка `in flight` появляется лишь когда в состоянии есть массив `plan` — у `supervise-task` его нет, и выдуманная строка была бы ложью. Чтение защитное (хелперы принимают `unknown`): Σ принадлежит навыку, чужой навык может назвать поля иначе, и тогда строка просто не печатается.

### 13.2 Чего сабагент не получает

- **Полной Σ.** Режим `full` не добавляли намеренно: он дублировал бы `task_show`, который возвращает и Σ, и процедуру P навыка, и напоминание о нотации. Сабагенту, который и есть исполнитель шага, дают MCP-инструменты — тогда он читает состояние сам, и это единственная копия.
- **Брифа базы знаний.** Не `SessionStart`: карта стоит токенов один раз на сессию, а сабагент стартует многократно.
- **Σ объявленных проектов** (`STATE3_PROJECTS`): он делегирован внутри этого проекта, а чужие состояния — контекст, которым он не может распорядиться.
- **Напоминания патчить Σ.** Хвостовые строки блока другие: «отчитайся — Σ владеет оркестратор» и «если `next.risk` destructive или external — остановись и сообщи, спрашивать пользователя его работа». Роль владельца состояния одна: два агента на одной Σ — это дважды закрытый пункт плана и `guard`-отказ как единственный след.

### 13.3 Что не делали и почему

- **Дифференциации по `agent_type`.** Соблазн очевиден: поисковому агенту ориентация не нужна, исполнителю нужна полная Σ. Но для пользовательских агентов хост отдаёт `agent_type: Custom` (`docs/features/hooks.md`), то есть различить `code-search` и `implementer` по payload нельзя, а список имён в настройках стал бы вторым источником правды, расходящимся с `~/.qwen/agents/`. Вместо этого — `STATE3_SUBAGENT_STATE=off` на весь хост и узкий `tools`-allowlist у самих агентов.
- **`SubagentStop`.** Событие отдаёт `agent_transcript_path` и `last_assistant_message` — готовый материал для автоматической сверки отчёта сабагента с реальностью (урок RaceGame: отчёту модели не верить). Не делали: сверка требует чтения диффа и запуска гейта, то есть отдельного решения о том, кто её исполняет и что делает при расхождении. Зафиксировано как направление.
- **Плагина opencode.** У opencode нет события старта сабагента, поэтому адаптер не менялся; его агент получает ориентацию только если хост сам её передаёт.

### 13.4 Правила делегирования в шаблоне

`templates/AGENTS.md` (§12.9) получил раздел «Delegating to subagents»: один владелец Σ, бриф вместо транскрипта, самый дешёвый подходящий агент и узкий allowlist (декларации инструментов — налог на каждый ход сабагента, включая девять наших), плата за ответ, а не за путь (вывод сабагента ложится в контекст оркестратора), «сначала проверь — потом запиши», и fork против именованного агента (fork наследует контекст и делит prompt-кэш родителя).

### 13.5 Проверки

build / typecheck / lint / format:check зелёные, **767 тестов / 40 файлов** (+9 к §12.8: extensions/inject-state 20→25, tasks/render 5→7, tasks/inject 18→20), `smoke:mcp` **31/31** через собранный `dist` — новая проверка гоняет хук с событием `SubagentStart` на настоящей базе и требует в выводе `goal:` и `next: ` при отсутствии `"artifacts"` и брифа. Vitest покрывает легаси-путь хука (ориентация вместо Σ, `blocked`, молчание при `STATE3_SUBAGENT_STATE=off`, отсутствие `## Supervised projects`, отсутствие брифа) и обе половины рендера (`renderTaskBrief` на dev-task и на чужом состоянии без `plan`, `readInjection` с опцией и без неё).

Событие сверили с установленным хостом, а не только с его документацией: `SubagentStart` присутствует в рантайме Qwen Code **0.23.3** (строка найдена в пяти чанках сборки), а живой headless-прогон перечислил все шесть агентов из `~/.qwen/agents/`. Чего эта сессия **не** проверила: что хост действительно вызывает наш хук на старте сабагента. Для этого нужен перезапуск Qwen Code (живая сессия исполняет старый код расширения и не подхватывает пересборку — см. README) и делегирование любому агенту: признак — в логе `[TRUSTED_HOOKS] Hook state3-subagent-state ended for event SubagentStart: success`, а в контексте сабагента блок `## Active task state (state3)` со строками `goal:` / `in flight:` и без JSON-состояния.

## 14. Дешёвая правка и проверяемая свежесть (19.09.2026)

Три отзыва пользователя на dogfood-прогон (`D:\Projects\AgeOfDrift\feedback`: `2026-09-18-state3-page-body-patch.md`, `2026-09-18-state3-state-compression.md`, `2026-09-18-state3-source-anchoring.md`) описывали одну болезнь с трёх сторон: **запись в state3 стоила дорого, а записанное нельзя было проверить**. Страницу приходилось переписывать целиком ради двух строк. Σ росла, и «сожми её» не помогало, потому что без разбивки по полям это приглашение переписать состояние наугад. Страница, описывающая код, не знала, что код с тех пор изменился, и читалась как текущая. Четвёртый отзыв (`2026-09-17-state3-c4-tree.md`, дерево C4, priority medium) в этот заход сознательно не реализован — это отдельная задача.

### 14.1 Тело страницы правится точечно

Было: `put` с новым `body`. Правка двух строк стоила перепечатки пяти тысяч символов, и по дороге можно было потерять абзац — молча, потому что единственной проверкой у вызывающего был его собственный текст.

Стало: `op patch` принимает до `MAX_BODY_EDITS = 20` правок трёх форм — `{find, replace}` (общий случай), `{after, insert}` (строка ниже якоря) и `{section, body}` (всё от заголовка до следующего заголовка того же или более высокого уровня; пустое `body` очищает секцию). Правки применяются по порядку, каждая к результату предыдущей, поэтому вторая может адресовать текст, который вставила первая. `op append` дописывает в конец через пустую строку — частый случай страницы `note`.

Два правила делают правку безопасной именно от модели. Адрес (`find`, `after`, `section`) обязан совпасть **ровно один раз**: неединственное совпадение посадило бы правку не туда, куда звали, и это хуже отказа — тело тогда читается как задуманное. И отказ не меняет **ничего**: правки применяются к копии и отбрасываются вместе, поэтому тело никогда не остаётся правленым наполовину. Отказ нумерует правку с единицы и называет причину (`edit 2 of 2 refused: find "scripts/" matches 2 times — send more surrounding text…`), а оба исхода несовпадения ведут к одному действию — скопировать текст из `page {"op":"get"}` дословно, потому что набранный по памяти якорь и есть причина отказа.

Unified diff не рассматривали всерьёз: номера строк — то, что модель считает хуже всего, тогда как адрес текстом она может скопировать.

Ответ пишет размер (`bodyWriteAnswer`): `Patched page car (2 edits) — body 96 -> 141 (+45 chars)`. Точечная правка доверяема именно потому, что не перепечатывает текст, — и тем же снимает единственную проверку, которая у вызывающего была; размер возвращает её. Модель, которая собиралась добавить строку и видит `4521 -> 812`, останавливается там, где голое «Updated» дало бы ей продолжить.

### 14.2 Прежние тела и лимиты, которые называют число

У Σ был аудит-след, у страниц — нет: страницу можно было прочитать только такой, какая она сейчас, поэтому абзац, потерянный при неаккуратной перезаписи, терялся навсегда, а на вопрос «кто это изменил и когда» ответа не было. `page_history` (`seq`, `page_id`, `at`, `body`) хранит последние `PAGE_BODY_HISTORY_LIMIT = 10` тел на страницу, записывается в той же транзакции, что и страница, и **не** индексируется в FTS: устаревшая версия не должна отвечать на поиск. Сохраняется тело, которое заменяют, а не новое — это текст, который читатель мог цитировать минуту назад, и после записи его больше никто не держит. `op history` перечисляет версии (`#seq`, дата, размер) или читает одну целиком по `revision`.

Отдельно — диагностика лимитов. Отказ схемы называет значение, которое перешло предел: `issueSizeDetail` превращает zod-`too_big` в `"summary" is 214 chars, limit 200`. Причина та же, что у размера в ответе на правку: на отказанной записи текст, который модель напечатала, уже потерян, и каждый ретрай стоит всего поля заново. Функция экспортирована из `src/core/validator.ts`, потому что база знаний валидируется zod'ом и должна сообщать лимиты так же, как задача.

### 14.3 Σ сжимается: архивация шага и delta-инжекция

Два порога: `STATE_SIZE_HINT_CHARS = 4000` (подсказка «сожми») и `STATE_DELTA_THRESHOLD_CHARS = 6000` (инжекция режется). Подсказка сама по себе не окупается — агент, который мог бы ужать Σ в середине шага, обычно этого не делает, — поэтому выше шести тысяч инжекция несёт только `goal`, `status`, `blockers`, `next` и шаг со статусом `in_progress`, а заметка называет, что оставлено (N шагов плана с разбивкой по статусам, N `artifacts`, N `decisions`, N `verifications`) и сколько весит вся Σ.

`injectedView` — единственное место, где Σ урезается: `renderTaskHead({injected: true})` зовёт хук, а ответы `task_show` и `task_patch` полные. Ответ патча — подтверждение записи, а `task_show` — вызов, чей контракт в том, чтобы вернуть всю Σ вместе с процедурой.

Архивация (`PlanItem.archived`) убирает готовый шаг из инжекции, оставляя его в Σ. Массив при этом **не** переписывается: шаг сохраняет индекс и id, поэтому path-ключ, записанный до архивации, адресует тот же шаг и после. Обе урезки сообщаются в одном дыхании с состоянием — инжекция, которая молча несёт меньше, чем Σ, хуже большой: возобновлённая сессия читает этот текст как авторитетную запись прогресса и обязана знать, чего она не видит. Подсказка о размере меряет хранимую Σ, а не вид (сжатие рендеринга ничего не меняет на диске) и подавляется, если delta-заметка уже сказала про размер.

`task_show {"view":"size"}` отвечает разбивкой по полям (`stateSizes` / `renderStateSize`): сколько символов стоит каждое, крупнейшие первыми, с долей и числом элементов — и **без Σ и без процедуры**, потому что оба и есть то, что измеряется; повторить их значит съесть то, что вызов экономит.

### 14.4 Адресация элемента: удаление и собственный id

Path-ключи умели менять элемент и добавлять, но не удалять: массив приходилось переотправлять целиком, то есть платить ровно за то, от чего path-ключи должны избавить. `{"verifications[2]": null}` теперь удаляет элемент. Удаление сдвигает индексы ниже, поэтому патч, удаляющий два элемента, применяется в порядке записи его ключей — это порядок, в котором патч читается, и единственный предсказуемый для вызывающего.

Вторая половина — `{"plan[id=5].notes": "…"}` и `{"plan[id=5]": null}`: элемент по его собственному id. Индекс и id расходятся немедленно, как только план записан: шаг с id `"5"` стоит на индексе 4, поэтому `plan[5].status` — вне диапазона, а `plan[id=5].status` — ровно то, что модель имела в виду. Оба отказа печатают пары `index → id` (не больше `LIST_LIMIT = 20`), потому что это единственное, что превращает отказ в исправленный ретрай, а не в догадку.

### 14.5 Проверки с временем и коммитом; предупреждение об `artifacts`

`verifications` теперь штампует рантайм (`stampVerifications`): каждая запись, которую патч добавил или изменил, получает `at` и `commit` до валидации и записи. Почему не агент: «pass» — утверждение о дереве, и без времени и коммита нельзя сказать, описывает оно состояние до починки или после — ровно та двусмысленность, в которую упирается супервизор, сверяющий отчёт с `git diff`. Агент честно не знает ни того, ни другого, поэтому спросили бы у него — получили бы догадки.

Идентичность записи для штампования — её содержимое без `at`/`commit`, а не позиция: патч, который удаляет или переставляет записи, сдвигает индексы, а запись, которая просто переехала, не записана заново. Содержательная идентичность заодно позволяет штамму пережить переотправку всего массива — а именно так приходит wholesale-патч. Неизменная запись сохраняет прежний штамп; запись, сделанная сборкой без штампов, остаётся без него, а не объявляется новой. Git зовётся лениво и не больше раза на патч: патч, который не трогает `verifications`, не платит за subprocess.

`src/core/git.ts` возвращает `null` вместо исключения — git может отсутствовать, проект может не быть репозиторием, дерево может быть посреди rebase. Запись состояния не должна падать из-за отсутствия контроля версий, а штамп, который не удалось снять, записывается как отсутствующий, а не угадывается (`GIT_TIMEOUT_MS = 5000`). `projectDirOf` при этом отличает проект от каталога состояния: `<project>/.state3` → `<project>`, а корень, указанный в другое место (`STATE3_STATE_DIR`, объявленный проект), принимается за проект сам — лучшего предположения нет, а родитель произвольного каталога привязал бы записи к дереву, которое к ним отношения не имеет.

Ключи `artifacts`, похожие на пути, проверяются на существование (`missingArtifactPaths`) — но это **предупреждение под ответом, а не отказ**: отказ заблокировал бы запись самого перемещения файла. Проверяются только path-like ключи (с расширением или с разделителем, без `://`), поэтому id страницы или фраза на языке пользователя не сообщаются как отсутствующий файл; в отчёте не больше пяти путей. Заметка добавляется только когда патч тронул `artifacts`: предупреждение на каждом патче учит пропускать хвост ответа, а в хвосте живут отказы.

### 14.6 Страница привязана к дереву

`page.source_commit` и `page.source_files` (миграция 2 → 3): запись сохраняет короткий хеш HEAD и файлы, которые тело называет. Коммит читается **в момент записи**, а не чтения — он должен говорить, каким было дерево, когда страницу писали; спросить позже значит ответить на другой вопрос.

Извлечение (`extractSourceFiles`) намеренно консервативно: ложное срабатывание стоит одной строки в отчёте, пропуск прячет страницу, которую надо было проверить. Токен считается файлом, только если оканчивается на известное расширение (`SOURCE_EXTENSIONS`) или несёт разделитель каталога, — версии, домены и обычные предложения отпадают; URL вырезаются до поиска; строковые ссылки (`:262-272`) отбрасываются, потому что якорь — файл, а номер строки и есть то, что перестаёт быть правдой; разделители нормализуются к `/`, как сообщает git. `SOURCE_FILES_LIMIT = 50`: страница, называющая больше, — листинг файлов, а не документ, и спрашивать git о сотнях путей на каждое чтение дороже, чем стоит якорь.

Якорь переставляется **только** когда меняется тело. Страница, у которой поправили `summary`, по-прежнему описывает тот же код, и перестановка якоря сообщила бы свежесть, которую никто не проверял — ту самую ложную уверенность, ради устранения которой якорь существует.

`page get` печатает три разных ответа (`renderFreshness`), и различить их важнее, чем показать: `unchanged since` — странице можно верить; `N commit(s) since` с файлами и коммитами — вот куда идти смотреть; `changed since: unknown (no git to ask)` — вопрос некому задать. Схлопнуть последнее в молчание значит позволить устаревшей странице читаться как текущая; на том же различии построена `freshness`, где `changed = null` (нет репозитория или страница старше якорения) не равно `changed = []` (не менялось). Страница, не называющая файлов, отвечает `names no file — nothing under it can go stale`: решения и намерения не устаревают от коммита.

`page {"op":"stale"}` (`renderStaleReport`) делает то же для всей базы, худшие первыми — по числу коммитов. Сканируются `STALE_SCAN_LIMIT = 100` самых свежих по `updated_at`, не архивные, с якорем, в отчёт идёт не больше `STALE_PAGES_LIMIT = 20`. Каждая страница стоит вызова git: отчёт, который делается минуту на большой базе знаний, не запускают на холодном старте — в единственный момент, когда его стоит читать. Страница, записанная на текущем коммите, пропускается без вызова.

В брифе git **не** вызывается (решение пользователя): карта проекта не должна платить за subprocess на `SessionStart`. Вместо отметки «код менялся» бриф несёт строку-подсказку `Pages are anchored to a commit; page {"op":"stale"} lists those whose code moved.`, на которую зарезервировано `FOOTER_RESERVE_CHARS = 160` символов бюджета.

### 14.7 Миграции

`MIGRATIONS[1]` — `page_history`, `MIGRATIONS[2]` — `page.source_commit` / `page.source_files`; `SCHEMA_VERSION = 3`. Каждый набор утверждений входит и в `SCHEMA_SQL`, поэтому база, созданная сегодня, и база, перенесённая со старой сборки, идентичны. База с более высокой версией отклоняется (fail closed): её писала более новая state3, и эта сборка не знает, что обязана сохранить. Триггеры поиска по-прежнему висят только на `page`, поэтому тела из истории в FTS не попадают.

Новые op появятся в работающей сессии только после перезапуска `qwen`; именно поэтому сквозные проверки в `smoke:mcp`, который запускает свой сервер из свежего `dist`, — единственный способ убедиться, что сборка их действительно отдаёт.

## 15. Ответ, которого не хватало: покрытие, дрейф, штамп и режим инжекции (20.09.2026)

Четыре отзыва пользователя на dogfood-прогон в AgeOfDrift (`2026-09-20-state3-doc-coverage.md`, priority high; `2026-09-20-state3-verifications-restamp.md`, priority high; `2026-09-20-state3-injection-rendering.md`, priority medium; `2026-09-20-state3-artifact-disk-staleness.md`, priority medium) описывают одну дыру с четырёх сторон: **state3 уверенно отвечал о том, чего не знал**. База знаний не могла сказать, чего в ней нет, — и «поиск ничего не нашёл» читалось как «в проекте этого нет». Σ не могла сказать, что дерево под ней сдвинулось, — и возобновлённая сессия рассуждала из посылки, которая перестала быть правдой ночью. Штамп проверки перезаписывался молча при сжатии Σ. Инжекция не говорила, в каком режиме пришла, и «Σ is 7294 chars» рядом с полным состоянием выглядело как сломанный порог.

### 15.1 Покрытие: какие файлы не записаны

`page {"op":"coverage"}` отвечает, какая доля документируемых файлов репозитория названа хоть одной страницей, и перечисляет неназванные — **чаще меняющиеся первыми**. Два вызова git отвечают на вопрос при любом размере дерева (`gitTrackedFiles` — `git -c core.quotePath=false ls-files`, `gitFileChurn` — один `git log -n CHURN_COMMIT_WINDOW=200 --format= --name-only`, из которого считается число коммитов на файл); `core.quotePath=false` обязателен, потому что база знаний пишется на языке пользователя, а git иначе напечатает `документация.md` как `"\320\264..."`, чего тело страницы содержать не может.

Ранжирование по churn, а не по алфавиту и не по размеру, — потому что вопрос звучит как «что дороже всего переоткрывать заново», а не «каких файлов больше». Файл, который меняли семь раз за последние 200 коммитов и о котором не написано ни слова, будет прочитан целиком ещё раз; файл, который не трогали три года, — нет. Окно в 200 коммитов ограничивает и стоимость вызова, и смысл ranking'а: «чаще всего менялся» — про сейчас.

В отчёт попадают файлы, которые страница в принципе может назвать (`isDocumentableFile` — то же правило, по которому `normalize` решает, что токен в теле является файлом: известное расширение или разделитель каталога), минус lock-файлы: их переписывает инструмент целиком, поэтому страница про `package-lock.json` была бы неправдой уже после следующей установки зависимости. Сравнение путей на Windows нечувствительно к регистру (`samePath`): `Scripts/Car.cs` и `scripts/Car.cs` — один файл, и назвать задокументированный файл дырой в документации значит один раз сделать отчёт таким, которому нельзя верить. `COVERAGE_LIMIT = 30` — в отчёт идёт начало списка, но полное число печатается всегда: честный ответ про живой проект это «531 файл, вот первые 30», а не листинг на пятьсот строк.

У файла, который никто не покрыл, нет «статуса» — есть только счёт. Поэтому ответ начинается с числа (`34 of 565 documentable file(s) are named by a page`), и проект без репозитория отвечает `this project has none to ask`, а не пустым списком, который читался бы как полное покрытие.

Измерено на живом AgeOfDrift: 34 из 565 файлов покрыты 30 страницами; первыми в списке неназванных идут `.qwen/settings.json` (8 коммитов) и `tools/CarApply.cs` (7) — второй это ровно тот файл, который сессия 19–20.09 читала целиком, потому что о нём не было ни строки.

### 15.2 Символы: поле, по которому поиск отвечает файлом

`page.symbols` — список строк вида `Name — path/to/file.ext`, не больше `SYMBOLS_LIMIT = 40` по `SYMBOL_MAX_CHARS = 200` знаков. Пределы выбраны так, чтобы поле оставалось указателем: сорок имён достаточно, чтобы ответить «где это живёт» про то, чему страница посвящена, и мало, чтобы соблазн вывалить туда все имена файла не окупился — для этого есть дерево.

Поле хранится отдельной колонкой FTS-индекса, а не дописывается к тексту тела, и это единственная часть шага, потребовавшая перестройки: FTS5-таблица не умеет `ALTER TABLE ADD COLUMN`, поэтому индекс снимается и пересоздаётся шестью колонками с переиндексацией `task` и `page` (`SEARCH_INDEX_SQL` — общий и для `SCHEMA_SQL`, и для миграции, поэтому свежая база и перенесённая идентичны, а расхождение невозможно по построению). Снимать триггеры обязательно: `CREATE TRIGGER IF NOT EXISTS` не заменяет существующий, и без `DROP` старые пятиколоночные триггеры остались бы на месте — каждый записанный после миграции символ молча отсутствовал бы в поиске. `tests/db/database.test.ts` воссоздаёт индекс и триггеры прежней версии руками и проверяет, что символ, записанный после миграции, находится: это ровно тот сбой, который тест «колонка существует» не ловит.

Веса `bm25(search, 0, 0, 10, 5, 1, 8)`: заголовок 10, summary 5, тело 1, символы 8. Символы выше тела, потому что строка там — готовый ответ с путём, а совпадение в теле может оказаться словом, упомянутым вскользь. `pickSnippet` тоже смотрит сначала в `symbols_snippet`: сниппет `- [RoadMask] — scripts/RoadNetwork.cs` экономит чтение страницы, ради чего поле и заводилось. LIKE-фолбэк (подстрока идентификатора, которую токенизатор не берёт) ищет и в символах.

Список сохраняется, когда его не прислали (`draft.symbols ?? decodeLines(current?.symbols ?? '')`) — как и всякое поле страницы: правка тела не должна стоить странице её указателя. `page get` печатает его блоком `symbols:` над ссылками и телом, а не прячет в прозе: это то место, которое читатель сканирует глазами в поиске «знает ли страница нужный мне символ». Файл из строки символа считается покрытием (§15.1): задокументировать символ и значит задокументировать файл, и отчёт, который требовал бы второго раза, требовал бы уже написанную страницу.

### 15.3 Промах поиска — это ответ, а не тупик

`nearestPages` на промахе называет до `NEAREST_PAGES_LIMIT = 3` страниц, ближайших по словарю: токены запроса и заголовка с summary (буквы и цифры, не короче `MIN_TOPIC_WORD_CHARS = 3`) сравниваются **по префиксу в обе стороны**. Префикс, а не равенство, потому что промахиваются обычно идентификаторами — `RoadNetwork` обязан оказаться рядом со страницей «Road network», а точное совпадение их не связывает никогда. Префикс, а не подстрока, чтобы `car` не стал совпадением внутри `scar`. Короткие слова отбрасываются: «the», «как» и «a» есть на каждой странице и не несут темы.

`renderSearchMiss` говорит три вещи по порядку: что ничего не нашлось и что это значит (ни одна страница и ни одна задача не содержат **всех** слов запроса), какие страницы ближайшие и какими словами они пересекаются, и куда идти дальше — grep по дереву, а найденное записать строкой символа, чтобы следующий поиск ответил файлом. Промах дороже попадания, если на нём остановиться: вызывающий уже заплатил за вопрос и узнал только то, что база знаний — не то место.

Отдельно разведены два случая, которые раньше выглядели одинаково: проект без страниц отвечает `this project has no knowledge base yet` и ведёт к `op "init"`, а не печатает «ближайших» из пустого множества. Поиск с `kind: "task"` списка страниц не печатает: вызывающий только что сказал, что страницы его не интересуют.

Внешний ripgrep для этой подсказки сознательно **не** зовётся (выбор пользователя): ноль зависимостей и ноль риска медленного скана на большом дереве, а путь «вопрос → файл» даёт §15.2 без единого subprocess.

### 15.4 Штамп проверки больше не теряется молча

Отзыв описывал сжатие Σ заменой массива `verifications` целиком (4 записи вместо 6), после которого у всех записей — включая старые — стояли `at` времени патча и `commit` текущего HEAD. Проверка выяснила две разные вещи. Сохранение штампа по идентичности содержимого в HEAD **уже было** (§14.5), но `identityOf` сравнивал `JSON.stringify` записи, то есть зависел от порядка ключей: `{"check":"npm test","status":"pass"}` и `{"status":"pass","check":"npm test"}` — одна и та же запись, а штамп перезаписывался. Порядок, в котором агент напечатал поля, не является частью того, что он зафиксировал, поэтому идентичность теперь каноническая: ключи сортируются рекурсивно (`canonical`), и переотправка массива в любом порядке штамп сохраняет.

Вторая половина — переформулировка. Запись с другим текстом это другое утверждение, и рантайм не умеет отличать сжатую формулировку от другой проверки, поэтому штамп переставляется по-прежнему. Изменилось то, что это больше не молча: `StampReport` считает `carried`/`stamped`/`superseded`, и под ответом патча появляется строка, называющая прежние `at` и `commit` каждой отцепленной записи (`stampWarnings`, не больше пяти с числом остальных). Прежние значения печатаются именно там, потому что больше им взяться неоткуда: `task_history` хранит патч **как он был прислан**, а агенту сказано `at`/`commit` не присылать, — то есть после перезаписи штамп не существует нигде. Та же строка пишется в историю (`HistoryEntry.note`, колонка `message` при `ok = 1`), поэтому `task_history` отвечает не только «что просили», но и «чего это стоило».

`keepStamp: true` из предложения отзыва не реализован: диагностика (§15.4, пункт 2 отзыва) закрывает потерю, а явное разрешение перенести штамп ослабляет ровно то свойство, ради которого штамп существует — что его проставляет рантайм, знающий HEAD, а не вызывающий. Вернуться к нему стоит, если сжатие Σ с переформулировкой окажется частым.

Процедура `P` в `DEV_TASK_STATE_DICT` дополнена правилом, которое агент может применить: запись, переотправленная с теми же значениями полей, штамп сохраняет (порядок не важен), запись с другим текстом штампует заново и ответ называет заменённый.

### 15.5 Дрейф артефактов: Σ описывает дерево, которое могло сдвинуться

`artifacts` говорит, **что** агент произвёл; `missingArtifactPaths` (§14.5) ловит путь, которого нет на диске, в момент записи. Между сессиями случается третье: путь на месте, Σ читается как текущая, а файл изменил кто-то другой. Сообщить об этом из Σ принципиально нельзя — Σ это запись того, что агент знал, — поэтому рядом с ней хранятся собственные числа файла.

Таблица `artifact_stamp (task_id, artifact_key, mtime_ms, size, at)` (миграция 3 → 4) пишется в транзакции каждого патча и сравнивается при чтении. Два решения определяют, будет ли это работать.

**Перештамповывается каждый патч, а не только тронувший `artifacts`.** Штамп означает «дерево выглядело так, когда Σ записали в последний раз», а патч и есть момент записи. Штамповать только на патче `artifacts` значило бы доложить собственные правки агента как дрейф на всё оставшееся время шага — шум ровно там, где предупреждение должно быть достоверным.

**Штампуются только обычные файлы.** mtime каталога меняется от любой записи внутри него, а ключи вроде `.qwen/tmp/` в Σ встречаются постоянно: штамп каталога сообщал бы дрейф всякий раз, когда агент положил туда временный файл.

Дрейф — это расхождение `mtime_ms` или `size`, либо исчезнувший файл; оба читаются одинаково (Σ описывает дерево, которого больше нет), но печатаются по-разному: `(modified 2026-09-19T23:43:12Z, 123 min after Σ was last written)` и `(no longer on disk)`. Минуты печатаются только когда mtime позже патча: checkout восстанавливает прежнее время, содержимое при этом другое, и «N минут позже» соврало бы про направление. Ключ без штампа пропускается, а не докладывается как «неизвестно»: его записала сборка без штампов, и следующий патч его снимет, а «не могу сказать» про каждый артефакт каждой старой задачи утопило бы то единственное, которое важно.

Читается в трёх местах и ни в одном лишнем: `task_show` (вызов, который возобновлённая сессия делает до того, как действовать по Σ), инжекция на `SessionStart` (`readInjection({drift: true})`; хук передаёт его только на этом событии и для корня, и для каждого наблюдаемого проекта супервизора) и `doctor` (не больше `DRIFT_FINDINGS_LIMIT = 10` находок, чтение обёрнуто в try — отсутствие таблицы штампов у старой базы не является дефектом). В обычном промпте строки нет: одна и та же строка на каждый ход сессии стоит дороже, чем сюрприз, о котором уже сообщили один раз. Сабагенту дрейф не инжектируется — он получает ориентировку, а не Σ, и чужие артефакты не его работа. `driftLines` в инжекции не бросает исключений: диагностика, которая уронила бы чтение, отняла бы у хода единственное, что у сессии есть.

Штампы живут в базе, а не в Σ, — и это не экономия ради экономии: Σ несётся в каждом промпте задачи, поэтому плата токенами на каждом ходу ради одного сюрприза раз в неделю была бы ровно той сделкой, против которой построен весь §14.3.

### 15.6 Режим инжекции печатается, а не угадывается

Отзыв увидел «Σ is 7294 chars — compress it» рядом с полной инжекцией и заключил, что дельта-режим не включился. Проверка показала, что порог срабатывает, но меряет не то число, которое печатается: `injectedView` сравнивает с `STATE_DELTA_THRESHOLD_CHARS = 6000` размер Σ **после** выброса архивных шагов (5867), а подсказка о размере называет размер сохранённой Σ (7294). Расхождение осмысленное — бюджет про то, сколько несёт промпт, и архивация уже расплатилась, — но изнутри неразличимое, и неразличимое оно было ровно до этой правки.

`InjectedView.mode = {kind, total, injected, archived}` теперь несёт оба числа, и печать зависит от случая. Дельта начинается со `Injection mode: delta — Σ is N chars, over the 6000-char budget…`. Полная инжекция, когда оба размера по одну сторону порога, не печатает ничего: строка режима стоила бы токенов на каждом ходу каждой задачи, чтобы сообщить то, что и так видно. Единственный случай, который стоит строки, — когда размеры расходятся по сторонам порога, и тогда печатается `Injection mode: full — Σ is 7294 chars and this prompt carries 5867 of them; the 6000-char budget measures what a prompt carries, not all of Σ…`. Строка появляется ровно тогда, когда без неё ответ выглядит как баг.

`task_show` называет сборку, которая ответила (`runtime: state3 0.1.0 (<loadedFrom>)`, с отметкой STALE, если `dist` старше `src`), — и только `task_show`, а не каждый ответ: это вызов, который делает возобновлённая сессия, а хост держит сервер, который он запустил, поэтому фича, существующая в репозитории, может не существовать в коде, который отвечает. В `view: "size"` строки нет — этот вызов отвечает про Σ и ничего больше.

Экранирование `>`/`<`/`&` в инжекции (`-&gt;`, `&lt;id&gt;`), на которое жаловался отзыв, делает **хост Qwen Code**, а не state3: в сыром stdout хука `->` без экранирования (проверено `--self-test`), `JSON.stringify` угловые скобки не трогает, а в репозитории нет ни одной функции экранирования. Убрать это со стороны рантайма нельзя; что можно — не искать в своём коде баг, которого там нет, и читать команды, которые надо скопировать дословно, через `task_show` (ответ MCP-инструмента в дополнительный XML-контекст не заворачивается). Это записано здесь, чтобы следующий прогон не потратил на то же самое час.

### 15.7 Миграции — и одна, которую пришлось разделить

`SCHEMA_VERSION = 6`: `MIGRATIONS[3]` — `artifact_stamp`, `MIGRATIONS[4]` — `page.symbols`, `MIGRATIONS[5]` — перестройка FTS-индекса под новую колонку. Каждый набор утверждений входит и в `SCHEMA_SQL`, поэтому свежая база и перенесённая идентичны. База более высокой версии по-прежнему отклоняется (fail closed).

Первые два из трёх шагов были одним, и это оказалось ошибкой, которую поймала только проверка на копии живой базы. Сборка, собранная между добавлением колонки и перестройкой индекса, проштамповала `user_version = 5` в двух настоящих корнях: в `D:\Projects\skillState` это сделал **хук** на первом же промпте после пересборки — `readInjection` открывает базу не read-only именно потому, что должен уметь её мигрировать, — а в `D:\Projects\AgeOfDrift` прогон `coverage` на живых данных. Такая база сообщает «схема текущая», имеет `page.symbols`, не имеет колонки в индексе и падает на любом `search` с `no such column: symbols`. Номер версии различить это состояние не может — значит, состояние надо превратить в переход: применённую миграцию не переписывают, а добавляют новую, и шаг `5 → 6` чинит индекс любой базе, которая успела проштамповаться пятёркой.

Проверено на копиях обеих баз, оригиналы на запись не открывались: `5 → 6`, индекс с колонкой `symbols`, счётчики строк прежние (AgeOfDrift: 19 задач, 30 страниц, 189 записей истории, 49 строк индекса, 35 связей; state3: 9/3/140/12/0), `quick_check = ok`, поиск отвечает, записанный символ находится и перестаёт находиться после удаления. Живые базы чинятся сами при первом открытии новой сборкой.

Урок стоит дороже самой правки: **промежуточную сборку нельзя оставлять в дереве, где живые базы открываются на запись**. Миграцию, которую автор собирается доработать, уже применил к проектам пользователя хук — на каждом промпте, а не только `npm run build`. Не собирать `dist` из незавершённой миграции нельзя тоже (тогда её не проверить); правильно — если собрал, добавить следующий шаг, а не править прежний.

### 15.8 Проверки

build / typecheck / lint / format:check зелёные, **991 тест / 50 файлов** (+3 файла к §14.9: `tasks/artifact-stamps`, `kb/coverage` на настоящем git-репозитории, `kb/symbols`), `smoke:mcp` **50/50** через собранный `dist` (+7 проверок: три про дрейф — молчание при совпадении, строка в `task_show`, строка в хуке на `SessionStart` и отсутствие её в промпте; одна про штамп — `Note: 1 verification stamp(s) are no longer attached…` при удалении элемента; три про базу знаний — `put` со списком символов, поиск по символу со сниппетом, в котором виден файл, и ближайшие страницы на промахе).

`tests/kb/coverage.test.ts` гоняет настоящий git-репозиторий, как `staleness.test.ts`: покрытие и churn — утверждения про git, и поддельный git проверил бы наш код против нашей же догадки о нём. `tests/db/database.test.ts` воспроизводит индекс и триггеры прежней версии руками, чтобы каждый шаг миграции испытывался против базы, у которой они действительно старые, включая ремонт проштампованной пятёркой (§15.7).

Три падения, найденные проверками по ходу. Два — про то, как тест читает ответ: smoke-чек «`{"verifications[0]": null}` удаляет элемент» грепал весь ответ и спотыкался о новую цитату штампа (переведён на строку Σ), а `databaseAtVersion` ронял `ALTER TABLE page DROP COLUMN symbols`, потому что SQLite не даёт удалить колонку, которую читает триггер (сначала снимается индекс с триггерами и возвращается прежний). Третье — само состояние из §15.7: его поймал не тест, а прогон миграции на копии живой базы, и это ответ на вопрос, зачем такой прогон вообще нужен в списке проверок.

## 16. state3: имя и дерево задач (26.09.2026)

Два изменения, которые пользователь сформулировал одной фразой: проект называется **state3**, и состояние становится древовидным — «задачи будут разделяться, а не в одном state тянуть задачу, которая ещё на очереди». Это не косметика рядом с сутью: имя отражает модель, а модель меняет то, что стоит в промпте на каждом ходе.

### 16.1 Что переименовано и что намеренно нет

594 замены в 70 tracked-файлах одним скриптом (`.qwen/tmp/rename-state3.mjs`, замены по регистрам: `SKILLSTATE_`→`STATE3_`, `skillstate`/`skillState`→`state3`, `SkillState`/`Skillstate`→`State3`) плюс `git mv` каталога `extensions/state3/`, лаунчера `bin/state3-mcp.mjs` и плагина `adapters/opencode/plugin/state3.js`.

Три вещи не переименованы сознательно:

- **Физический каталог `D:\Projects\skillState`.** Его переименование сломало бы `cwd` живой сессии, запущенный MCP-сервер и линк расширения — то есть ровно те три вещи, которыми проверяется результат. Скрипт защищает абсолютный путь к нему от замены, поэтому `opencode.json` и примеры в README указывают на настоящий каталог и на новые имена внутри него.
- **`SKILL.state`** — имя метода из статьи (arXiv:2608.26263), а не имя проекта. Оно осталось в прозе и в `description` пакета; переименовать его означало бы потерять ссылку на источник.
- **Формат данных.** Ни имя файла `state.db`, ни схема, ни легаси-раскладка `<id>.json` + `<id>.history.jsonl` слова `skillstate` не содержат, поэтому база, написанная прежней сборкой, читается новой без преобразования содержимого.

Обратная совместимость env-переменных (`SKILLSTATE_*` → `STATE3_*`) не делалась: в окружении пользователя не оказалось ни одной (§16.2 сообщает о переносе вслух, а предупреждение «нужна сборка state3 … задайте `STATE3_HOME`» и без того называется переменную, которую надо задать).

### 16.2 Корень состояния переносится сам и отказывается делать это вслепую

`.skillstate/` → `.state3/` — `src/tasks/migrate-root.ts`. Три ограничения, из которых ни одно не случайно:

- **Копирование, а не перемещение.** Старый каталог остаётся: на Windows каталог с открытым файлом всё равно не удаляется, а обмен «восстановимый дубликат» на «невосстановимую потерю» — плохая сделка для единственной копии истории проекта.
- **Отказ, если рядом лежит `state.db-shm`.** SQLite держит `-shm`, пока соединение открыто, и убирает его при чистом закрытии, поэтому файл означает: базу прямо сейчас кто-то пишет. В обычном случае это **прежняя сборка того же сервера в сессии, которая ещё не перезапущена**. Скопировать базу из-под пишущего — значит получить рваный файл, а рваная копия Σ хуже отсутствия копии: она читается как достоверная. Ответ — `in-use`, и он печатается: хуком в stderr, сервером в баннер, CLI одной строкой, `doctor` как finding.
- **Только обычный корень проекта.** Перенос срабатывает, когда `basename(rootDir) === '.state3'`; корень, заданный `--root` или `STATE3_STATE_DIR`, — это каталог, который кто-то выбрал сам, и его сосед не наше дело.

Подключено в пяти точках, и порядок важен: хук и плагин opencode сначала проверяют `existsSync(state.db)` и только потом зовут сборку, поэтому перенос вызывается **до** этой проверки (`carryOverStateRoot`, экспортированный из `dist/tasks/inject.js` рядом с `readInjection`). Без этого переименованный проект читался бы как проект, в котором состояния никогда не было. В `readInjection` отказ переноса возвращается как `kind: 'unreadable'`, а не `'none'`: «здесь ничего нет» — единственный по-настоящему неверный ответ, который эта функция может дать.

Ворота в хуке и плагине сделаны на `existsSync` по трём именам, а не на загрузке сборки: проект без состояния не должен платить за `import` dist на каждом промпте. Из JS зеркалится только имя каталога (`LEGACY_STATE_DIRNAME`), правило целиком живёт в сборке — так же, как уже зеркалятся `STATE_DIRNAME` и `STATE_DB_FILENAME`.

Копия оставляет на диске второй корень, который по-прежнему выглядит достоверным, и это единственное место во всём переименовании, где работа теряется молча: что-то, направленное на старый корень (хост с прежним линком расширения, скрипт с `--root .skillstate`, второй проект на той же сборке), пишет состояние, которого новый корень никогда не увидит, а `task list` отвечает в обоих. Поэтому маркер хранит не только путь и время копии, но и `mtime`/размер исходного `state.db`, а `divergedSource()` сравнивает: если старый корень писали после переноса, `task doctor` печатает `warn`, и ту же строку несёт инжекция **на старте сессии** — не на каждом промпте, как дрейф артефактов (§15.5). Автоматического слияния нет и не будет: у двух разошедшихся историй нет честного слияния, задача — сделать расхождение невозможным не заметить.

Сравнение стоит один `stat` и не читает файл: хэш был бы точным, но облагал бы налогом каждый старт сессии, а ловить надо ошибку, сделанную за часы, а не внутри одного тика часовой метки. Это и есть известный предел — запись, попавшая в тот же тик, что и копия, невидима (в тесте две записи разнесены на 30 мс именно поэтому), а на файловой системе с грубыми метками окно слепоты равно грубости меток. По одному размеру судить нельзя: SQLite переиспользует страницы, и в прогоне реальная запись в старый корень оставила `state.db` ровно той же длины (118784 → 118784 байт) — сдвинулся только `mtime`, на 47 мс.

### 16.3 Дерево: `parent`, статус `pending` и порядок очереди

`task.parent TEXT REFERENCES task (id) ON DELETE SET NULL` + `INDEX task_parent`, `SCHEMA_VERSION 6 → 7`. `SET NULL`, а не `CASCADE`, как у `page.parent`: работа, пережившая декомпозицию, в которую её положили, остаётся работой, а сироту видит `doctor`, тогда как каскад был бы тихой потерей данных.

**Статус `pending` пришлось добавить** (`TASK_STATUSES = pending | active | blocked | done`). Без него три созданные подряд подзадачи все оказываются `active`, и прежнее правило «последняя обновлённая открытая задача» отдаёт **последнюю созданную** вместо первой по очереди: декомпозиция, ради которой всё затевалось, переворачивает очередь. Подзадача создаётся `pending`; порядок выбора — `active` > `pending` > `blocked`, а внутри ранга тай-брейк разный по смыслу ранга: у очереди это порядок создания (никто ещё не трогал), у `active`/`blocked` — `updated_at` (кто-то был в середине, и возобновлённая сессия должна попасть туда же).

Очередь выше блокера не случайно — это поправка по живому прогону 26.09.2026. Фронт работ отвечает на вопрос «что можно делать сейчас», а заблокированная задача по определению не может. При обратном порядке одна задача, припаркованная две недели назад решением пользователя, вставала впереди семи готовых кусков, и холодная сессия получала её Σ с текстом «не начинать без решения пользователя» вместо следующего куска работы. Что при этом теряется, тоже надо назвать: задача, которую только что заблокировали, больше не всплывает сама, если в проекте есть готовая очередь. Она остаётся доступной по id, видна в `task_list`, а на старте сессии её называет строка `Also open elsewhere`. Если готовой работы нет вовсе, заблокированная по-прежнему выбирается — и тест «still lands on a blocked task when nothing is ready to work on» держит именно это, потому что агент должен уметь разблокировать её, не выясняя сначала id.

**Порядок очереди — `(created_at, rowid)`, и `rowid` здесь не избыточен.** Миллисекундного `created_at` не хватает: агент, дробящий задачу на три части, создаёт все три внутри одной миллисекунды, и без порядка вставки «первый кусок работы» определялся бы случайным суффиксом id. На этом попался smoke-прогон: обе подзадачи родились в одну миллисекунду (видно по одинаковой base36-метке в id), и инъекция взяла вторую — вместе с ней пропала строка `Queued after this` и сработала отрицательная проверка «Σ соседа не в промпте». Правило одно на три места: `queueOrder()` в `store.ts`, `CASE WHEN status = 'pending' THEN rowid END` в `FRONTIER_ORDER` и `(created_at > ? OR (created_at = ? AND rowid > ?))` в запросе очереди.

### 16.4 Что несёт промпт: ветка вместо очереди

Кандидат на инжекцию — **фронт работ**: открытая задача, под которой ничего не открыто (`NOT EXISTS` по `parent`). Задача, которую раздробили, — контейнер, и инжекция контейнера вернула бы в промпт ровно то, что дробление должно было из него убрать.

Поверх Σ листа добавляются не больше двух строк:

```
Branch: <цель корня> [status] -> <цель середины> [status] -> this task
Queued after this: "<цель следующего брата>" (<id>) + N more — task_list prints the tree.
```

Ветка отвечает на «какой кусок большой работы я делаю», очередь — на «что будет после», и обе стоят строк, а не состояний: Σ братьев в промпт не попадают вовсе. Строка очереди не даётся делегированному сабагенту (`queue: false`): ему вручили один кусок, и назвать следующий — значит пригласить его начать его самому.

Обе строки описывают **своё** дерево, и холодный прогон на копии живой базы показал дыру: фронт работ выбирает одну задачу, а декомпозиция не бывает выбранной — родитель контейнер, его куски только в очереди. Когда в проекте активен посторонний корень, инжекция не называет чужую очередь вообще, и сессия без контекста начинает новую работу рядом с уже раздробленной, вместо того чтобы продолжить её. Поэтому на старте сессии добавляется третья строка — `Also open elsewhere: 8 queued in 1 decomposition, 2 other open roots — task_list prints the tree.` Считаются открытые задачи за вычетом своей ветки и братьев (их уже покрыла строка очереди). Только на старте, по тому же правилу, что дрейф и расхождение корней: в проекте всегда есть открытые задачи, до которых не дошли руки, и строка на каждом промпте стала бы постоянным налогом за неизменное сообщение.

Все строки ветки идут **над** Σ, а не под ней: возобновлённая сессия читает сверху вниз, и «это часть вот этого» должно предшествовать состоянию, к которому оно относится. `branchLines` не бросает исключений и при сбое возвращает то, что успело собрать: потерять Σ из-за сбоя в её аннотациях — неверный обмен.

### 16.5 Декомпозиция закрывается последней

Задача с открытыми подзадачами не переходит в `done` — ни через `task_patch` (`reject('guard', …)` с записью в историю отказов), ни через `task_finish`. Правило живёт в store, а не в guard'е навыка: guard читает одно состояние, а подзадачи — другие строки. Считать нужно по строкам, а не по саммари: подзадача, чей скилл этому рантайму неизвестен, выпадает из `list()`, но родителя держать обязана, иначе работу можно закрыть поверх.

Создать подзадачу под несуществующим или закрытым родителем нельзя: декомпозиция — это утверждение, что родитель ещё в работе.

### 16.6 Поверхность: десятого инструмента нет

Декларации инструментов стоят токенов в каждой сессии, поэтому дерево добавлено в существующие девять: `task_start` получил `parent`, `task_show` — `view: "tree"` (декомпозиция по строке на задачу, без Σ и без процедуры), `task_list` печатает дерево с отступом и счётчиком `(N subtasks, M open)` на родителе. Порядок обхода — общий (`treeOrder()` в `render.ts`): CLI и MCP-инструмент рисуют одно и то же дерево, потому что два форматтера одной формы разъезжаются. В CLI добавлены `--parent` и `--tree`.

Сирота (родитель, которого в выборке нет) печатается как корень, а задача, не обойдённая из-за цикла, — плоско в конце: «каждая задача присутствует в списке» — единственное свойство, которое список обязан сохранить при любом виде дерева.

### 16.7 Миграции

Шаг `6 → 7` — две инструкции (`ALTER TABLE task ADD COLUMN parent …`, `CREATE INDEX task_parent`). Колонка в `CREATE TABLE task` стоит **в конце**, как `page.source_commit`: раскладка свежей базы и базы, дошедшей миграциями, совпадает. `tests/db/database.test.ts` откатывает версию, снимая сначала индекс и только потом колонку, — SQLite не даёт удалить колонку, которую читает индекс.

### 16.8 Проверки

build / typecheck / lint / format:check зелёные, **1027 тестов / 52 файла** (+2 файла: `tasks/migrate-root` — 13, `tasks/tree` — 18), `smoke:mcp` **56/56** через собранный `dist` (+6 проверок дерева: подзадача создаётся `pending` и отвечает «Queued as a subtask of …», `task_list` печатает дерево со счётчиком на родителе, `task_show {"view":"tree"}` отвечает декомпозицией без Σ, инъекция несёт `Branch:` и `Queued after this:` и **не** несёт `"goal":"<следующий брат>"`, старт сессии называет чужую очередь строкой `Also open elsewhere: …`, закрыть родителя при открытых подзадачах нельзя).

Что проверки поймали, кроме порядка очереди из §16.3: тест `databaseAtVersion` не умел откатывать седьмую версию и падал с `duplicate column name: parent` — то есть миграция испытывалась бы на базе, которая и так новая. Отрицательная проверка в smoke («Σ следующего брата не в промпте») — единственная, которая измеряет выигрыш дробления, а не только его механику: без неё дерево могло бы инжектировать ветку и всю очередь разом, и все остальные проверки остались бы зелёными.
